# Claude Code adapter

Use this adapter only after inspecting the current session's visible tools, permissions, and skill listing — Claude Code's own surfaces change across versions. Evidence below is public Claude Code documentation verified on 2026-07-22: [Subagents](https://code.claude.com/docs/en/sub-agents), [Skills](https://code.claude.com/docs/en/skills), [Worktrees](https://code.claude.com/docs/en/worktrees), [Workflows](https://code.claude.com/docs/en/workflows), [Permission modes](https://code.claude.com/docs/en/permission-modes), and [Tools reference](https://code.claude.com/docs/en/tools-reference). Current-session observations carry their own dates below; undated observations are from 2026-07-22.

## Capability mapping

- `delegate_readonly` — `Agent(subagent_type: "Explore")`. Built-in and read-only: Write and Edit are denied. [Subagents](https://code.claude.com/docs/en/sub-agents)
- `delegate_parallel` — issue multiple `Agent` calls in one message. Subagents run in the background by default and deliver results as a completion notification on a later turn, not an immediate return; wait for that notification before reporting results. [Subagents](https://code.claude.com/docs/en/sub-agents)
- `delegate_model_select` — the per-invocation `model` parameter on the `Agent` call. `haiku` is a genuinely lower tier, suitable for the weak-model probe; `opus` and above suit the hardest slices. [Subagents](https://code.claude.com/docs/en/sub-agents)
- `delegate_write_isolated` — public docs document `isolation: worktree` as a field on a subagent definition (`.claude/agents/*.md` frontmatter or `--agents` CLI JSON), not as an `Agent`-call parameter ([Worktrees](https://code.claude.com/docs/en/worktrees)). Some sessions additionally expose a call-time `isolation: "worktree"` on `Agent` and on the `Workflow` tool's `agent()` options (current-session observation, 2026-07-22). Trust only what the current session's schema actually shows; without a confirmed isolation path, implement slices sequentially.
- `delegate_persistent` — current-session observation, 2026-09-06: a background `Agent` returns a completion notification; `SendMessage` with `to` set to its name and a `message` resumes it from its transcript, including after completion. `ListAgents` lists addressable agents. The observed `Agent` schema selects `model` (`sonnet` / `opus` / `haiku` / `fable`) but exposes no effort parameter; effort is not selectable there. Alternatively, `mcp__codex__codex` with `prompt`, `sandbox: "workspace-write"`, and the repo as `cwd` returns a thread ID; continue that implementer with `mcp__codex__codex-reply` using `threadId` and `prompt`, inspecting each synchronous result. Codex effort can be supplied through `config` with `model_reasoning_effort`; this is a Codex setting, not an `Agent` effort tier. If none of these persistent paths, including the agmsg peer below, is confirmed, use the ordinary sequential slice loop.
- Persistent agmsg peer — current-session observation, 2026-09-06: use `~/.agents/skills/agmsg/scripts/spawn.sh codex <name> --boot-prompt "<task>" --project <path> --team <team>` or an already-running Codex peer, then `send.sh <team> <from> <to> <message>` from that scripts directory. The observed Codex peer used agmsg `turn` delivery: `delivery.sh status codex <project>` reported `mode: turn`, and the Stop hook in `.codex/hooks.json` delivered inbox messages at turn end. This is the primary confirmed path in that setup, distinct from a Claude Code `Monitor`. To prompt an idle peer to start a turn after a send, issue `tmux send-keys -t <pane> '$agmsg'` and then `tmux send-keys -t <pane> Enter` as separate calls: combining text and Enter left the text unsubmitted in the observed TUI. Confirm the turn started with `tmux capture-pane -p -t <pane> | tail`. Use the placement recorded by `spawn.sh`, or inspect `tmux list-panes -a -F '#S:#W.#P #{pane_current_command}'` to identify the intended peer. For a fresh peer without turn/monitor delivery, include in `spawn.sh --boot-prompt` both the phase task and this instruction: "Start a background inbox poll every 600 seconds using inbox.sh for your team and name; keep inspecting its live output and implement each received phase." For example, run `while true; do sleep 600; ~/.agents/skills/agmsg/scripts/inbox.sh <team> <name>; done` through Bash, then observe that running process between work items. This is the user-requested polling fallback; its latency is up to the interval while output is being observed, and the tmux nudge remains the low-latency option. A detached poll alone does not establish that an idle agent consumes its output. Without a confirmed delivery and reply path, treat this persistent capability as unavailable.
- Goal continuation — current-session observation, 2026-09-06: sending a literal `/goal ...` over agmsg to a Claude Code peer remains unverified; it does not establish a way to put an `Agent` subagent into goal mode. The Codex TUI has a separate goal mechanism; see [codex.md](codex.md) for the observed replacement dialog and continuation limits. Use the phase prompt and explicit follow-up messages when goal support is unconfirmed.
- `skill_discovery` / `skill_invoke` — the available-skills listing (names plus descriptions) loads into context at session start; invoke with `Skill(skill="grilling", args="...")` — and separately `Skill(skill="domain-modeling", ...)` or `Skill(skill="tdd", ...)` when selected ([Skills](https://code.claude.com/docs/en/skills)). Skills whose frontmatter sets `disable-model-invocation: true` (upstream's `grill-me` / `grill-with-docs` wrappers) are omitted from this listing even when installed; treat their absence as expected, not as "companion missing". Current-session observation: the listing can carry both a working-diff `code-review` skill and a namespaced `code-review:code-review` skill that reviews an already-open GitHub PR via `gh` — the latter does not apply pre-push. Check which is actually present before invoking either.
- `plan_artifact` — if the session was launched in plan mode and handed a specific plan-file path, use that file directly ([Permission modes](https://code.claude.com/docs/en/permission-modes)). Otherwise mirror to `~/.claude/plans/<slug>.md` as the native convention (current-session observation, 2026-07-22). The common workflow's `/tmp` artifact stays primary.
- External review (Phase 2 / Phase 4) — current-session observation, 2026-07-22: prefer `mcp__codex__codex` when it resolves as a deferred tool, called with `sandbox: "read-only"` and the target repo as `cwd`. If it is not connected, fall back to `Skill(skill="codex:rescue", args="--effort high --wait <prompt>")` — this path is write-capable by default, so the prompt text must include, verbatim: "This is a read-only review. Do not make any edits to any files." There is no flag that enforces this; it has to live in the prompt. An `agmsg` exchange is eligible only if it creates a fresh reviewer with enforced read-only execution. If none of these produce a review, follow the no-reviewer path in [external-review.md](../external-review.md) rather than silently skipping the gate.
- `human_confirmation` — an explicit user go-ahead before commit is a standing norm in this environment, not a platform enforcement: the permission classifier generally auto-allows commits to the current branch, so this gate depends on actually asking ([Permission modes](https://code.claude.com/docs/en/permission-modes)). `AskUserQuestion` gives structured confirmation but is denied to subagents — the orchestrator asks ([Tools reference](https://code.claude.com/docs/en/tools-reference)).
- Slice fan-out via the `Workflow` tool requires the session's explicit opt-in per that tool's own rules; never invoke it on the orchestrator's initiative. [Workflows](https://code.claude.com/docs/en/workflows)

## Safety

- A persistent implementer writes into the shared working tree, so the manager must not edit code while the loop runs; it verifies the diff and checks before sending the next phase.
- `bypassPermissions` and `dontAsk` modes remove the interactive checks this workflow's gates depend on; confirm the session's actual permission mode before treating any capability above as confirmed. [Permission modes](https://code.claude.com/docs/en/permission-modes)
- The `codex:rescue` write-capable default is the single highest-risk gap in the review chain — an omitted verbatim read-only line makes it silently write-capable, not silently read-only.
