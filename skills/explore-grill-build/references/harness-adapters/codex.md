# Codex adapter

Use this adapter only after inspecting the current session's visible tools, permissions, sandbox, and writable roots. Codex may delegate when the user or applicable project or skill instructions request it, but the current tool menu and policy determine what can actually run. [Subagent guidance](https://learn.chatgpt.com/docs/agent-configuration/subagents#triggering-subagent-workflows)

## Capability mapping

- Delegate independent survey or review work only when the session exposes a subagent mechanism. State the division of work, whether to wait, and the required result in each prompt.
- Use parallel delegates only for read-only, independent exploration. The orchestrator must synthesize and verify their results.
- Treat a delegate as an external reviewer only when a fresh context and an enforced read-only sandbox are both confirmed. Invoke tools with only fields present in the current schema.
- External review — use Claude Code started from tmux with the review command in [claude-code.md](claude-code.md), so Opus or Fable reviews and evaluates findings. Observed on 2026-10-31 from `codex exec --sandbox workspace-write` with codex-cli 0.166.0-alpha.6: `tmux new-session` failed with `error connecting to /private/tmp/tmux-501/default (Operation not permitted)`; a socket in the workspace failed with `error creating ./egb.sock (Operation not permitted)`; calling `claude -p` directly returned `Not logged in · Please run /login`, exit 1. The unsandboxed path is unprobed: the launching Claude Code session's permission classifier denied starting `codex --sandbox danger-full-access`. Under workspace-write, mark this reviewer unavailable and follow the no-reviewer path in [external-review.md](../external-review.md), or have the human or an outside session run the command. A human may grant an unsandboxed session; the skill keeps the current sandbox unless that authorization is given.
- Use the common `/tmp` plan artifact first. Mirror it only when Codex exposes a writable, persistent plan path; do not assume a Claude-compatible plan location exists.
- Inspect current approval and sandbox constraints before delegating writes. Without confirmed isolated write environments, implement slices sequentially.
- Persistent implementer — current-session observation, 2026-09-06: Codex can keep the implementation context in an MCP thread, started with `mcp__codex__codex` using `sandbox: "workspace-write"` and the repo as `cwd`, then continued with `mcp__codex__codex-reply` using `threadId` and `prompt`. An agmsg peer is another persistent path: in the observed setup, `delivery.sh status codex <project>` reported `mode: turn`, and the Stop hook in `.codex/hooks.json` delivered the inbox at turn end. To start a turn in an idle peer, use the separate text/Enter tmux nudge in [claude-code.md](claude-code.md); that adapter also describes the user-requested polling fallback for peers without turn/monitor delivery. In the other direction, a Claude Code peer with its `Monitor` running receives agmsg messages through `watch.sh` without a tmux nudge. Confirm delivery and an inspectable reply in the current session before relying on either path; otherwise use the ordinary sequential loop.
- Implementer CLI — `codex exec` starts the implementer and `codex exec resume` continues its session; see [Implementer CLI](claude-code.md#implementer-cli) for the model/effort mapping, exact commands, and 2026-10-31 observations from Claude Code. Confirm the path in the current session before use.
- Goal mechanism — current-session observation, 2026-09-06: Codex exposes a TUI `/goal <objective>` command and `get_goal` / `create_goal` / `update_goal` tools, with continuation fragments between turns. The inspected mechanism registers goal tools in app-server sessions with persistent thread state (including the TUI), not mcp-server sessions; an MCP implementation thread alone does not establish goal support. In the manager's TUI observation, sending `/goal <objective>` as text and then `Enter` in separate tmux calls showed `Replace goal?` for an existing goal; a further confirmation displayed `Goal active`. A new phase objective therefore replaces an existing goal rather than adding another one: preserve the user's active objective unless replacement is authorized. The implementer completed Phase 2 and replied while its user-requested inbox polling remained active; goal auto-termination was not established. The manager-reported delivery observation and the implementer transcript attribute Phase 2 to the turn-mode Stop hook, before the first scheduled poll; the poll did not deliver that phase.
