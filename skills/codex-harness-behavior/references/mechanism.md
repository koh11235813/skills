# Codex Harness Mechanism

This file is the mechanism behind the operational model in SKILL.md — how each layer described there is actually built, down to the byte and millisecond limits, plus the complete rejection-string table that SKILL.md only summarizes as keyword triage.
Read SKILL.md first for the mode matrix, the fast triage table, and the two playbook sections; come here when those don't resolve what you're seeing, or when you need an exact limit, constant, or the full string list.
Evidence for every claim in both files lives in `references/provenance.md`, keyed by a re-greppable fragment rather than a commit — treat figures here as current behavior, not as a historical record.

## Layer 0 — governance ceiling

Set before the session; neither the agent nor the user can raise or lower it mid-run. SKILL.md states the operational shape of each item below; this is the detail it doesn't have room for.

- **The "force exact value" set's actual keys**: beyond approval policy, sandbox mode, and web-search mode, the same mechanism reaches `sqlite_home`, `log_dir`, `model_catalog_json`, `check_for_update_on_startup`, `allow_login_shell`, and the Windows `sandbox_private_desktop` flag. Most of these are bookkeeping, but two aren't — `allow_login_shell` and the Windows private-desktop flag change exec semantics directly, not just which options a UI shows. Four auth keys are the exception to the "any layer can set it" rule: `allowed_login_methods`, `allowed_chatgpt_workspaces`, `cli_auth_credentials_store` and `chatgpt_base_url` are stripped from any backend-delivered (`EnterpriseManaged`) layer before validation and take effect only from a locally installed one. When a stored credential is disallowed by whichever layer did set them, the auth manager filters it to `None` rather than reporting a rejection — codex presents as logged out.
- **Of the four managed-requirement sources, only the cloud-delivered one is account-gated.** The system, legacy `managed_config.toml` and MDM layers are separate `RequirementSource` variants that load regardless; the backend-delivered bundle needs codex-backend auth *and* a Business, Education or Enterprise plan (Team and the self-serve Business tiers are excluded, and header auth reports no plan at all, so it never qualifies). An org policy that is simply absent points at the plan or at header auth rather than at the mechanism.
- **Workload identity is env-selected, host-owned and irreversible.** The presence of `OPENAI_FEDERATION_RULE_ID` or `OPENAI_IDENTITY_TOKEN_FILE` selects workload identity for the whole process; a partial set fails validation at startup rather than falling back to another credential source. Once active the mode cannot be replaced (`set_external_auth` returns a permanent error), cleared, or logged out (`PermissionDenied`), and `codex mcp-server` refuses to start under it at all. An embedder driving the app-server therefore cannot switch accounts at runtime.
- **Bedrock is two auth modes, not one, and both sit on the API-key side of each auth gate below.** `bedrockApiKey` stores a bearer token; `bedrockAccessKeys` stores an AWS access-key ID, a secret access key and an optional session token, and carries that same name on the app-server wire. Both are false in `uses_codex_backend()` and in `has_chatgpt_account()`, and both are exempt from the workspace check, so `allowed_chatgpt_workspaces` never applies to them. Both also count as the `api` login method, and that classification splits into two very different outcomes: `allowed_login_methods = ["chatgpt"]` only filters the credential to `None` (above), while the separate, ordinary-config `forced_login_method = "chatgpt"` key is enforced a second time at `codex exec` and TUI startup (skipped under workload identity) — that path clears every configured auth store and exits 1 with `ChatGPT login is required, but an API key is currently being used. Logging out.` Setting only the first key leaves the credential on disk; setting the second deletes it.
- **Managed hooks' auto-trust path fails closed**: a hook shipped inside a workspace plugin installed or updated from a marketplace under the active account gets its content hash auto-recorded as trusted right after a successful plugin refresh — a second, non-manual route to "trusted" status alongside manual grants. If the trust-record write fails, or the account changes mid-process, this route fails closed rather than trusting anyway.
- **The bundled cleanup-hook allowlist is a hard-coded exception to the hash rule, and the source calls it temporary.** `ALLOWLISTED_BUNDLED_HOOKS` names seven plugin IDs. Six are ordinary MCP targets — `browser@openai-bundled`, `chrome@openai-bundled`, `chrome-dev@openai-bundled`, `chrome-internal@openai-bundled`, `computer-use@openai-bundled` and `unified-computer-use@openai-bundled` — each covering `Stop`, `Interrupt` and `SubagentStop` against the `turn_ended` tool on `node_repl` (`cua_repl` for the unified one). The seventh, `browser@openai-curated-remote`, covers only `Stop` and `SubagentStop`, targets `browser.turn_ended` on `codex_apps`, and additionally requires an empty input template and the registered connector `connector_openai_browser`, because raw Apps tool names can collide and identity has to be resolved against the caller's enabled tool catalog. That last requirement splits the allowlist by hook *source*: local plugin hook discovery has no tool catalog and passes `None` for the connector, so a locally installed plugin can only ever match the six MCP entries; the Apps entry resolves only on the executor plugin path, which looks the connector up — and those executor-sourced handlers are then pushed into the same local engine already stamped `builtin`. A match also requires an `mcp_tool` handler and no matcher; a command handler, a matcher, or any other tool name falls straight back to the ordinary hash path. That one `builtin` flag forces `HookTrustStatus::Trusted` with no recorded hash, forces `enabled` regardless of per-hook state, and survives construction of the engine with the hooks feature off, which retains exactly the builtin handlers and clears every warning and load error so a disabled-hooks session cannot fail startup on them. Two things still bound it: only active — enabled and error-free — plugins contribute hook sources at all, and `allow_managed_hooks_only` filters the source out before the allowlist is ever consulted. The classification is deliberately invisible to clients rather than merely unadvertised: `HookRunSummary.builtin` is `serde(skip)`, absent from the JSON schema and the TS declaration, and not deserializable from an inbound payload, so a client can neither read it nor forge it; the app-server's hook catalog — the only consumer of the hook listing in the tree — drops builtin entries; and lifecycle notifications are suppressed for them while telemetry is kept.
- **On a remote executor the same predicate runs inverted.** Executor plugin hook discovery retains *only* allowlisted bundled cleanup hooks and discards every other executor plugin hook, with a `FIXME` marking the filter as temporary until executor plugin hooks can be trusted. Executor-side plugin hook coverage is therefore this allowlist and nothing else — the opposite failure mode from the local side, where the allowlist adds hooks that ordinary trust would have blocked.
- **The model catalog's per-model `tool_mode` field is read unconditionally before any local feature flag** — there is no branch where local config overrides a catalog value. The shipped catalog currently sets `tool_mode: code_mode_only` for seven slugs (`gpt-6-astra`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-daybreak-blue-latest`, `gpt-daybreak-red-latest`, `codex-auto-review` — treat the list as volatile and check `tool_mode` rather than memorizing it). **This is not an edge case any more**: the highest-priority visible preset, which is what an unconfigured session gets, is `gpt-5.6-sol`, and the next two after it are also `code_mode_only`. Assume you are in code mode until the tool list says otherwise, rather than the reverse. See "Code mode" under §6 for the runtime mechanism this leads to.
- **The catalog channel is wider than `tool_mode`.** The same model entry also supplies collaboration-mode instruction text (`collaboration_modes`, preferred over the harness's local templates), `model_specialty` (see §2's cyber note), and `experimental_supported_tools`, a per-model allowlist that gates the two async user-facing tools. The model you dispatch to therefore determines not only which tools exist but what your mode instructions say. Note the allowlist's compatibility quirk: `request_user_input_async` is registered when the catalog advertises either its own name **or** the retired `send_user_message_async`, and the catalog supplies that tool's description under the old key too, so a catalog that has never been renamed still turns the current tool on. Three further fields on the same entry behave the opposite way round from `tool_mode` — explicit local config wins wherever a local channel exists, and the catalog only supplies what was left unset. `multi_agent.mode` gives Multi-Agent V2 its delegation posture (see §6); `model_messages.token_budget` can activate token budgeting and the history/notes extension at thread startup (see §6); and `model_messages.tools.send_user_message_async.description` is the description text for `request_user_input_async`. That last one is documented in the protocol type to leave the description empty rather than disable the tool when the string is empty, and the handler honors it — the built-in description is substituted only for a missing or null value, never for `""`.

## 1. What the agent sees before acting

The harness assembles the agent's entire world. Key injection layers, in rough order:

- **System prompt**: chosen per model; overridable by config; persisted across resume. Mid-thread model or personality switches do NOT rewrite it — they inject `<model_switch>` / `<personality_spec>` developer messages that retrain the agent in place.
- **Permissions announcement**: a developer message wrapped in `<permissions instructions>` states the sandbox mode, approval policy, writable roots, denied reads, and pre-approved command prefixes. It explicitly teaches which escalations are futile, e.g. "Approval policy is currently never. Do not provide the `sandbox_permissions` for any reason, commands will be rejected." and "NEVER provide a prefix_rule argument for destructive commands like rm." Re-injected on any policy change. These are default strings, not guaranteed: a server-supplied model catalog can override the announcement text for any approval policy, and a separate catalog field can independently override the sandbox-mode section.
- **Environment context**: a user-role `<environment_context>` fragment with cwd, shell, date, timezone, network allow/deny domain lists, and filesystem access entries. Only diffs are re-sent mid-session — a bare new cwd can appear with no explanation. The sandbox and network policy are disclosed up front here, not just enforced later. One element is feature-gated: with `powershell_shell_version` (under development, default off) and a turn resolving to a single local environment whose shell is PowerShell, the fragment also carries a `<shell_version>` holding that shell's `major.minor`, probed once per shell path under a 2-second timeout and yielding a version only when the shell exits cleanly with at most 64 bytes of stdout — the result, a miss included, is memoized process-wide, so a shell that probes badly once is never retried in that process. Its removal is explicit rather than silent: a version that was reported and then goes missing renders as `<shell_version status="unavailable" />`, the same shape a vanished environment gets.
- **AGENTS.md**: project-scoped discovery is skipped entirely when the active project is marked untrusted — host-provided user instructions still load, every `AGENTS.md` in the tree does not, with nothing in the delivered context saying so. Otherwise: collected from project root down to cwd (an `AGENTS.override.md` beats `AGENTS.md` per directory), concatenated with separators, under a total byte budget (`project_doc_max_bytes`, default 32 KiB, configurable). The file straddling the budget is byte-truncated mid-file, later files dropped whole — nothing in the delivered text marks the cut, and the only trace of the cut existing at all is a server-side log line the model never sees. The byte budget is one pool shared across *all* selected environments, not a per-environment limit: it is consumed in environment order, so a secondary environment's `AGENTS.md` can contribute zero bytes purely because an earlier one was large. When a filesystem sandbox applies, a discovered-but-unreadable file returns an `io::Error` reading `` failed to load AGENTS.md instructions for environment `{id}` `` rather than degrading to no instructions; the swallow-and-log path survives only for environments with full disk read access. Changes are re-injected with explicit replace/expire notices.
- **Marker protocol**: every harness-injected user-role fragment carries start/end markers (`<permissions instructions>`, `<environment_context>`, `<external_…>`, `<codex_internal_context …>`, `<current_time_reminder>`, `<user_shell_command>`, `<recommended_plugins>`, `# AGENTS.md instructions` — whose body is itself wrapped in `<INSTRUCTIONS>`). The human UI hides these; the markers are the agent's only signal that text is harness-authored rather than typed by the user. The one exception is IDE context: the client splices it into the user's own text item with no marker, separated only by `## My request for Codex:`.
- **The rule is user-role only.** Developer-role startup composition carries its own markers (`<skills_instructions>`, `<apps_instructions>`, `<plugins_instructions>`, `<multi_agent_mode>`) but also an unmarked block: the multi-agent usage hint arrives as a bare developer message of its own. A dump at this pin is three developer messages plus one user message, and marker absence in the developer role therefore carries no information about authorship.
- **Trust labeling**: host-provided context arrives either as user-role `<external_KEY>value</external_KEY>` (untrusted — quarantined, not instructions) or as developer-role `<KEY>value</KEY>` (application-trusted). Values over ~1,000 tokens are middle-truncated with a literal `…N tokens truncated…` marker.
- **`<git_attribution>`**: an extension installed unconditionally in both app-server and mcp-server contributes a developer-role fragment. Enabled, it orders every commit message you write or amend to end with `Co-authored-by: Codex <noreply@openai.com>` — including in the `message` argument when a GitHub app or plugin tool creates the commit — every PR body to carry `Generated with [Codex](https://openai.com/codex/).`, and explicitly tells you to ignore earlier instructions that disabled attribution. It is driven by the backend account setting `commit_attribution_enabled`, not by local config: resolved with a 5-second timeout, cached in the thread store against the auth generation, and deferred 30 seconds after a failure. Non-Codex-backend auth and fetch failures both resolve to disabled. The opposite, disabled fragment is emitted only when the previous world state was enabled or unknown — from an absent prior, disabled contributes nothing.
- **Skills**: the skills catalog budget resolves in three steps (`skill_metadata_budget()`): a configured `max_context_tokens`, capped at 10,000 tokens; otherwise 2% of the resolved context window; otherwise a flat 8,000-*character* budget, which is what any surface passing no window gets. Descriptions are capped, then shortened, then whole skills are dropped by scope priority when over budget. A `$skill-name` mention injects that skill's entire body as a `<skill>` fragment — but only when exactly one enabled skill matches; ambiguous mentions are silently skipped with no error. Note what this does *not* pull in: only the skill's own top-level body is injected, so a `references/` tree ships with the skill at zero injection cost and is read on demand with file tools. This is the `$mention` path only. Skills are also reachable as ordinary tool calls with a different visibility boundary — see "Skills delivery" under §6.
- **Tool menu**: recomputed for every sampling request. Deferred tools are invisible until discovered via tool search. Oversized tool schemas — over 5,000 bytes, a round decimal threshold, not 5 KiB — are compacted progressively in up to four stages, each attempted only if the schema is still over budget after the last one: strip descriptions, drop schema definitions, collapse deeply-nested objects toward the root, then prune schema compositions (constructs like allOf/oneOf/anyOf). There is no marker recording that compaction happened, or which stage it stopped at. Separately from size, the harness models every tool schema with a fixed whitelist struct — `$ref`, `type`, `description`, `encrypted`, `enum`, `items`, `minItems`, `properties`, `required`, `additionalProperties`, `anyOf`/`oneOf`/`allOf`, `$defs`, `definitions` — and because that struct declines no unknown key, every other JSON Schema keyword is silently discarded when the sanitized value is deserialized into it: numeric bounds, `minLength`/`maxLength`/`pattern`, `format`, `default`, `maxItems`, `uniqueItems` and `title` never reach the model. This is a property of the representation, not of the size policy — it happens on the no-compaction parse path too, and in the compacting path the drop lands *after* all four passes, at deserialization. Some discarded keywords leave a trace first: `const` is rewritten into a one-element `enum`, and on a node that declares no `type` a numeric keyword infers `number` and `format` infers `string`, so `{"minimum": 1}` parses to `{"type": "number"}`. A node with no `type` whose only keywords are discarded ones is cleared outright instead — `{"maxLength": 5}` becomes `{}`, a property the model sees with no type at all. The 5,000-byte budget is itself measured on this normalized form, so the size check already runs against the lossy schema.
- **Reminders**: periodic timestamps ("It is YYYY-MM-DD HH:MM:SS UTC."), now wrapped in `<current_time_reminder>` markers and delivered on the **developer** role rather than as bare user text, a token-budget warning when nearing compaction, and cross-thread budget notices as thresholds are crossed.
- **Goal steering**: hidden fragments between turns push back on scope-shrinking ("Do not substitute a narrower, safer, smaller... solution") and order wrap-up when budget runs low. Objectives are XML-escaped and labeled as user-provided data to blunt prompt injection. The model also gets three plain-named tools for the same object — `get_goal`, `create_goal`, `update_goal` — registered in app-server sessions that have a persistent state DB and are not review subagents (mcp-server never installs the extension at all). `goals.max_goal_token_budget` is unset by default; once configured it is both the default budget for a new goal and a hard ceiling, and an over-budget request comes back naming both numbers. Budget is not confined to the thread that owns the goal: a child thread charges its token usage to the *root* goal's accounting state, and nesting is transitive because each thread resolves its root through its parent's own root — so a subagent's spend lands in the root goal's `tokens_used` and can trip the same `tokens_used + delta >= token_budget` comparison that flips it to `BudgetLimited`. Goals also self-block, but only in code mode: at turn stop, once three qualifying turns have accumulated, the active goal is set to `Blocked` with the reason `execution-unavailable`, and a turn qualifies only when a default-namespace tool named `exec` failed *after* its handler actually ran, with no tool completing successfully in that turn. `exec` there is the code-mode tool (`PUBLIC_TOOL_NAME`), not `shell` or `exec_command` — those tools cannot feed the streak at all, so a session that is not in code mode never auto-blocks no matter how many commands fail. Everything else is neutral rather than counted — a failure raised before the handler ran, a non-`exec` tool's failure, an ordinary unsuccessful result, a blocked or aborted call, a turn with no tool calls at all: none of these increment the streak, and none of them reset it either. Three things reset it: any tool completing successfully, the streak's goal being replaced, and a Plan-mode turn, which clears the turn's goal outright at turn start. The block is also skipped if the goal that was active while the streak accrued is no longer the thread's goal by the time turn stop runs, so a replacement goal never inherits its predecessor's failure history.
- **Hooks at intake**: prompt-submit and session-start hooks can inject developer-role context, or veto the turn entirely — a blocked prompt never reaches the model at all.
- **Fragment count**: the harness implements roughly 40 distinct injectable context fragments in total — a few more raw implementation sites exist, but some of those are test-only fixtures or duplicate wiring rather than a distinct fragment. The bullets above are the load-bearing ones; two clusters this document had never named before are a realtime/voice fragment family and a family of `Legacy*Warning` fragments. Worth knowing specifically: `approved_command_prefix_saved` and `network_rule_saved` fire after a proposed prefix or network rule is actually persisted, telling the model in-band that it happened. That narrows the self-escalation claim in §2 that "suppressed suggestions give the model no feedback" — that claim is only about suggestions that get suppressed. A rule that does get saved is echoed back through one of these two fragments on a later turn.

## 2. What happens when the agent acts

### Tool dispatch

- Unknown tool name → `unsupported call: {tool}` returned as a failed tool result; the turn continues.
- Parallel tool calls return in emission order regardless of completion order; a tool not marked parallel-safe takes an exclusive lock and serializes against everything.
- **PreToolUse hooks** run before dispatch. A hook can veto — `Command blocked by PreToolUse hook: {reason}. Command: {command}` for a `Bash` or `apply_patch` call carrying a command string, `Tool call blocked by PreToolUse hook: {reason}. Tool: {tool_name}` for everything else — or silently rewrite the tool's input. The rewritten command executes; the agent only sees the output of what actually ran, not what it asked for.
- **The model's command surface is `exec_command` + `write_stdin`, and it is conditional.** The old built-in `shell` / `shell_command` tools are gone. `add_shell_tools` returns early — registering **nothing** — unless the turn has an environment, the `shell_tool` feature is enabled, and the model's `shell_type` is not `Disabled`. If any of those three gates fails the agent has no built-in command tool at all in that sampling step, with nothing saying so. The `unified_exec` feature is a fourth condition but it does not gate the surface: with it enabled you get `exec_command` plus `write_stdin`; with it disabled (which managed requirements are the only path to) you get a **one-shot** `exec_command` and no `write_stdin` at all. The one-shot spec drops `tty` and `yield_time_ms`, drops `session_id` from the result, and adds `timeout_ms` defaulting to 10,000 ms; the process is terminated on timeout or cancellation and cannot be resumed. Read the shape of the tool, not the presence of a shell tool, to know which you have. A session id returned by `exec_command` is the handle `write_stdin` polls, and a second `environment_id` parameter appears when more than one environment is selected. The `shell` **parameter** is not another tool: its value is parsed only to detect *which shell type* was requested, after which codex resolves the binary through its own discovery and falls back if the type is unrecognized — a model cannot point it at an arbitrary executable. It is present unless execution is local zsh-fork with no remote environment; local zsh-fork rejects an explicit `shell` with `` `shell` is not supported for local zsh-fork exec ``. The name `shell_command` survives in two other places: as a legacy model-catalog alias coerced to unified exec, and as the app-server's `thread/shellCommand` request — which by design "runs unsandboxed with full access rather than inheriting the thread sandbox policy", making it an escape hatch the thread's own sandbox mode does not constrain.
- **Tool-name collisions delete tools silently.** The registry refuses any external tool using a reserved name and drops any duplicate key, logging `skipping external tool with reserved name` locally — the model sees only a shorter menu. A collision is turn-fatal only when `tool_registry.error_on_tool_collisions` is set (default false). If a *non-MCP* external tool never appears, a name collision is a live hypothesis.
- **MCP tools are the exception to that rule — they are renamed, not dropped.** Names are sanitized and de-duplicated before registration, with a 12-hex sha1 suffix appended to the colliding namespace or tool name and any name over 128 bytes truncated and hashed the same way, so two servers exposing the same tool name both survive. Registration keys off the already-normalized name, so MCP-versus-MCP collisions never reach the registry's duplicate drop; only a collision against a non-MCP tool can still delete one. The legacy `mcp__` prefix is on by default but switchable (an under-development feature plus a per-server opt-out list), so a callable MCP tool name is not derivable from the server's config — read it out of the tool list. A missing MCP tool is therefore evidence of catalog, authority or exposure filtering, not of a name collision.
- **The standalone `web.run` tool ships a conversation tail with every call.** Where it is registered instead of the hosted `web_search` tool (a responses-lite model, or the under-development `standalone_web_search` feature, on a provider advertising web search and namespaced tools), each call automatically sends the search backend the previous user text message, up to 1,000 tokens of assistant text that followed it, and the current user message. The model does not choose what leaves.
- **The `clock` tools have two independent gates, and turning on current-time reminders can take one of them away.** `clock.curr_time` is registered when the `current_time_reminder` feature is enabled **or** the model's catalog entry lists `clock` in `experimental_supported_tools` — in the shipped catalog only the hidden `gpt-6-astra` does, and hidden entries are skipped when the default preset is picked, so a default-configured session has no clock tools at all. `clock.sleep` needs the `sleep_tool` feature, which is stable and default-**on**, so that gate is rarely the thing withholding it; what decides is the mode. `always_on` registers sleep whenever the feature is enabled. The default `model_driven` mode *branches* on the reminder feature rather than combining with it: with reminders enabled, sleep is decided solely by `current_time_reminder.sleep_tool` (default false) and the catalog advertisement is no longer consulted; with reminders disabled, it falls back to that advertisement. Enabling current-time reminders without also setting the sub-flag therefore **removes** `clock.sleep` from a model that had it by default. The two tools are not a package — `curr_time` without `sleep`, and `sleep` without `curr_time`, are both reachable.
- Shell commands receive `CODEX_SESSION_ID` and `CODEX_VERSION` alongside `CODEX_THREAD_ID`, in addition to the sandbox markers in §3. `CODEX_VERSION` is the harness's own crate version, and the harness re-asserts it four separate ways so a configured value never reaches the command: `inject_session_env` writes it *after* the shell environment policy has already been applied, overwriting whatever that policy's `set` produced; the translation of that policy into the exec server's own policy drops the key from `set` case-insensitively and force-adds it to `exclude`; the exec-server overlay re-sends it even when it already equals the local policy value; and a shell snapshot that exports a stale `CODEX_VERSION` is overridden by an export replayed after the snapshot is sourced. Reading it tells you the running harness, never anything an operator configured. The same version rides outbound MCP request metadata as `codex_version` — attached to MCP tool calls, hook invocations and extension-tool requests, and inserted after client-supplied metadata has been merged, so a client-supplied `codex_version` is silently overwritten.

### Command classification (exec policy)

Every shell command is classified allow / prompt / forbidden before anything spawns, and the worst matching decision wins — one forbidden rule overrides any allow.

- `bash -lc` scripts are parsed with a real bash grammar. Only plain word-commands joined by `&& || ; |` are decomposed and checked segment by segment. Any subshell, redirection, substitution, control flow, or parse error forfeits the built-in per-command auto-approval — the script becomes one opaque command vector that no rule anchored on the inner command can match, though an explicitly configured prefix rule (e.g. anchored on `bash -lc`) can still match the whole vector and decide it. A separate literal-word check tightens this further: `is_literal_word_or_number` rejects any tree-sitter word starting with `=` or containing any of `{ } * ? [ ] \ ~ ^ # $` or a backtick, on the grounds that the shell rewrites them at runtime. One failing word makes `parse_shell_lc_plain_commands` yield nothing, and `commands_for_exec_policy` then falls back to `vec![command.to_vec()]` — so `ls *.md`, `rm -rf build/*`, `cat ~/x` and `mv f{a,b}` never lower to plain argv, and the whole unparsed wrapper becomes both the policy subject and the proposed exec-policy amendment. This closes the "safe-cmd && unsafe-cmd" smuggling hole.
- With no safelist left, an unmatched, non-dangerous command outside the Windows no-backend guard is decided by three inputs: approval policy, filesystem sandbox kind, and whether the call requests a sandbox override. Under `never` it runs (the sandbox is the protection). Under `unless-trusted` it always prompts. Under `on-request` an unrestricted or externally-sandboxed filesystem runs it, and a restricted one runs it too unless `sandbox_permissions.requests_sandbox_override()` is set, which prompts.
- `rm -f`/`-rf` (even via sudo, even inside a parsed sequence) forces a prompt — or outright rejection when prompting is disabled. Detection is deliberately broad: it also catches forced rm hidden inside `env`-wrapped invocations, `trap ... EXIT` bodies, pipelines, `if`/`for`/`while` control flow, `$(...)`/backtick substitution, nested `bash -c`/`sh -c`, and force flags placed after the operand (`rm /tmp/x -f`) — not just the direct/sudo form. A closed loophole: under policy `never` with the sandbox explicitly disabled, a dangerous-rm match used to be silently allowed; it is now always forbidden. Its own rejection string comes in two forms — `` `{command}` rejected: rm -f style commands are not permitted. Use a safer approach `` when the heuristic drives the decision to `Forbidden`, and the same sentence bare, with no `rejected:` prefix and no command, when `Granular` policy rejects a heuristic-driven prompt; see §4 for when neither appears.
- When policy forbids prompting, would-be prompts convert to rejections with exact strings like `approval required by policy, but AskForApproval is set to Never`.
- A forbidden command never spawns: `` `{command}` rejected: policy forbids commands starting with `{prefix}` ``.
- **`untrusted` is now internal-only.** `approval_policy = "untrusted"` in `config.toml`, a profile, or a `-c` override fails config load with `approval_policy = "untrusted" is no longer supported; remove this setting`, and the CLI's `--approval-mode` enum no longer spells it. Two paths still produce it: a project whose trust record marks it untrusted gets it as the resolved default, and an app-server client can pass it on `thread/start` — that arrives as `ConfigOverrides.approval_policy`, which is applied *after* the rejection and so is never checked. Managed requirements can also pin it as the required default. Under it, every command no exec-policy rule explicitly allows returns `Decision::Prompt`. `UnlessTrusted` is the only policy for which the default `wants_no_sandbox_approval` returns true for *every* tool — `Granular` returns true only when its `sandbox_approval` flag is set, `OnRequest` and `Never` never do, and the apply_patch runtime overrides the default to accept `OnRequest` too — so a classified sandbox denial can earn one approval-gated second attempt outside the filesystem sandbox — unless the filesystem policy carries denied-read restrictions, which keep every attempt sandboxed.
- **Environments can carry their own restrictive exec policy.** An environment's policy is merged as an overlay over the active command policy. One containing allow rules is rejected at environment setup with `environment command policy cannot contain allow rules`, so the overlay can only tighten — the same command can therefore be allowed in one environment and prompted in another.

### The approval gate

When a prompt is required, the tool call suspends on a channel until a decision arrives. Precedence: permission-request hooks → extension approval reviewers → guardian LLM reviewer → human. An installed extension can claim a review and return the decision before the full Guardian pass runs — but any request that asks for escalated sandbox permissions, and any approval retry, sets `require_synchronous_review` and bypasses the extension shortcut entirely, so an auto-approving extension cannot wave an escalation through.

- Hooks can allow or deny without the human ever seeing a prompt; an allow is indistinguishable from user approval.
- The guardian (when enabled) is an LLM judge; denial reads `This action was rejected due to unacceptable risk.` plus a rationale.
- Human denials are normalized to exactly `exec command rejected by user` / `patch rejected by user`. A denied terminal write is **not** normalized that way — it keeps the reviewer's own reason and reaches the model wrapped as `write_stdin rejected: {reason}`; and because that prompt offers only approve and abort, an ordinary denial there comes from a hook or the Guardian reviewer rather than a human declining one call.
- Client, deserialization and transport failures during approval fail closed to a denial, but can retain `approval request failed` as their model-visible reason — the normalization above applies only to an exact human rejection. Inspect the reason instead of treating every rejection as a human denial.
- **A cached command-approval lookup serializes the selected environment's exec-policy fingerprint together with a seven-field key** (`UnifiedExecApprovalKey`): environment id, the raw first argv token (`executable: command.first().cloned()` — nothing is resolved, so it is the shell token for a shell-wrapped invocation and the program token for a direct exec), the canonicalized command, cwd, `tty`, the sandbox permission profile, and a separate optional additional-permissions profile. The fingerprint is an eighth reuse condition on top of those seven, and all of it must match for a cached approval to be reused, so the two permission profiles are independent conditions rather than one, toggling a TTY request invalidates a previously-cached approval, and approving one shell binary never carries to another even when the parsed inner command is identical. Changing directory invalidates an approval. The command field is canonicalized before it becomes part of the key — wrapper-path variants collapse together in that field (`/bin/bash -lc X` and `bash -lc X` canonicalize identically, though the separate executable field still tells them apart) and recognized bash and PowerShell scripts are rewritten to a canonical placeholder form — so commands that read differently can share a single approval, which is the opposite of an exact-match cache. Only `ApprovedForSession` decisions are written into that store — a denial is never cached, so a denied command is re-adjudicated rather than auto-refused.
- Choosing "abort" on an exec or patch approval prompt tears down the whole turn, not just that call. MCP tool approvals are the exception: they travel through the user-input path rather than the exec-approval op, and an abort is caught inside the MCP call path and converted back into a tool result (`user cancelled MCP tool call`) rather than a teardown.
- **A client answering a `request_permissions` call may set `strict_auto_review` with turn scope**, which for the rest of that turn routes every approval to the Guardian reviewer ahead of the normal per-policy choice. On the MCP path it additionally cancels three separate shortcuts — the `never`-plus-unrestricted-profile auto-approval, the per-tool approval-mode check (which covers both the `auto`-mode read-only annotation skip and a config-persisted `approve` mode), and the remembered session approval — so an MCP tool that ran unprompted on the previous turn can be reviewed and denied on this one. It is not MCP-specific (exec and network approvals read the same flag), and there is no managed-config path that turns it on at this pin.
- **Terminal input can be reviewed too, under a default-off feature — and where it cannot be enforced it is refused, not prompted.** With `write_stdin_approval` (under development, default off) enabled, a non-empty `write_stdin` is compared against the permissions retained from that terminal's launch and against the turn's current policy before any byte reaches the process. Three cases skip the check outright: the feature being off — which is the default state of every session — an empty poll, and a `\u{3}` sent to a non-TTY process. Past that, the terminal's original environment must still be selected, or the write is refused with `cannot access the terminal's original environment; select it before retrying`; the Guardian path enforces the same condition in its own wording. Two conditions then refuse instead of asking, because an approval cannot retrofit a sandbox onto a running process: the current environment owns a network policy and the terminal either bypassed the sandbox at launch or was launched under a different one; or the current baseline carries denied-read restrictions and the terminal either bypassed the sandbox or its filesystem context has drifted. Network settings are normalized out of that second comparison, so pure network drift falls through to the graded review below rather than being refused. What remains is graded: matching permissions need no approval at all unless turn-scoped `strict_auto_review` is set, while retained additional grants, a launch-time sandbox bypass, and any other policy drift all require one. Before the reviewer is consulted, two shapes are refused on their own — a NUL byte in the input (`terminal input contains a NUL byte and cannot be reviewed safely`, because manual approval shell-quotes the input and cannot carry one), and an oversized review: the formatted guardian action plus its reason must fit 8,000 bytes, and a formatter that truncated the action refuses on the same string, so no unreviewed tail is ever executed. A write that needs any sandbox override also meets the ordinary approval script first: under `never`, or a Granular policy with sandbox prompts off, it is rejected with the usual `approval required by policy…` string and no reviewer runs, unless `strict_auto_review` is set under `never`. **The human prompt for a terminal write is deliberately narrow.** It travels the ordinary exec-approval op, but the offered decisions are pinned to `Approved` and `Abort` alone — no per-call decline and no `ApprovedForSession` — so every reviewed write re-prompts, and a human who refuses tears the turn down rather than declining the call. The reason text built for the reviewer names the launch authority (`This terminal was launched outside the sandbox…`, `This terminal retains additional permissions.`) and serializes the retained grants as JSON; it is reviewer-facing and never reaches the model.
- **A managed `auto_review.required_on_models` slug coerces the config at startup, then validates it.** The session constructor runs first: on a listed slug, and outside a trusted-Guardian-reviewer session, it downgrades `danger-full-access` to workspace-write, recomputes the network policy, and sets `approvals_reviewer = AutoReview` — erroring only if the managed `approvals_reviewer` requirement itself refuses that value. `validate_auto_review_requirement` runs afterwards, over the already-coerced config, so it passes; it bites only when the `guardian_approval` feature is off, or on a *later* `SessionSettings::apply`, and its message is `To use model X, you need to use auto review.` MCP *reviewer selection* is forced to Guardian by the same requirement, ahead of any per-app reviewer setting — but reviewer selection only decides who reviews. The three skip-review shortcuts above (auto-approval, per-tool `approval_mode`, remembered session approval) are evaluated separately and still fire, so a tool persisted as `approval_mode = "approve"` runs unprompted even on a required-auto-review model.
- **A remembered MCP approval is keyed by connected account; a persisted one is not.** `McpToolApprovalKey` is four fields — server, `connector_id`, `link_id`, tool name — and `persistent_mcp_tool_approval_key` delegates to the session key, so both decisions are looked up at the same granularity. Two conditions suppress the key entirely: the resolved approval mode must be `Auto` (`AppToolApproval` is `Auto`/`Prompt`/`Writes`/`Approve`), and on the `codex_apps` server the call must have resolved a `connector_id`. When either fails there is no key at all, and because the prompt's `allow_session_remember` and `allow_persistent_approval` flags are literally `key.is_some()`, the remember and persist options are not offered rather than offered and discarded — such a call is re-prompted every time. The asymmetry is in what `ApprovedMcpPolicyAmendment` writes when a key does exist: `persist_codex_app_tool_approval` sets `apps.<connector_id>.tools.<tool>.approval_mode = "approve"`, with no `link_id` segment, and the per-tool mode is consulted ahead of the per-account default — so an approval that was account-scoped in memory becomes app-wide. A successful write also reloads the session's user config layer, but app-tool policy is evaluated against the `McpConfig` captured in the prepared call, so treat the widening as taking effect from the next run. A failed write degrades to the in-memory record, which stays account-scoped.

### Self-escalation is scripted away

- Requesting escalated permissions when the policy doesn't allow it earns an immediate corrective rejection: `approval policy is {policy}; reject command — you cannot ask for escalated permissions if the approval policy is {policy}`.
- The model may propose a reusable allow-prefix rule, but interpreter prefixes are banned, and only an explicit user decision persists the rule. The banned list is large (88 entries, up from an earlier 46) and covers essentially every shell (`bash`/`sh`/`zsh`/`dash`/`ksh`/`fish`/`cmd`/`powershell`/`pwsh`), interpreter (`python3`, `node`, `ruby`, `perl`, `php`, `lua`, `Rscript`, `julia`, `deno`, `bun`), and package-runner (`npm run`, `pnpm run`, `yarn run`) invocation, plus `rm` and `sudo` themselves — not just a handful of illustrative examples.
- A one-shot startup migration enforces this retroactively: on first launch of a version that ships the enlarged banned list, any previously-saved custom allow-prefix rule in the user's rules file that now matches an entry on that list is silently deleted, and a marker file then records completion so the migration never re-runs. A prior "always allow" for a shell/interpreter/`rm`/`sudo` prefix can vanish across an upgrade with no in-band notice.
- Suppressed suggestions (ones that get banned or otherwise not persisted) give the model no feedback at all. Rules that do get persisted are the opposite case: the next turn carries an `approved_command_prefix_saved` or `network_rule_saved` context fragment confirming exactly what was saved — see the fragment-count note in §1.
- **Cyber-specialty models and managed `auto_review.ignore_rules` slugs lose every allow rule.** `TurnContext::allow_prefix_rules()` returns `AllowPrefixRules::IgnoreForCyberModel` when the catalog gives the model `model_specialty: "cyber"` or the managed requirements' `auto_review.ignore_rules` list contains the slug. `current_for_prefix_rules` then rebuilds the policy with every `PrefixRule` whose decision is `Allow` filtered out; prompt, forbidden, network and host-executable entries survive. `auto_amendment_allowed` is set to `allow_prefix_rules == Honor`, so in this mode no reusable prefix-rule amendment is proposed either. The unmatched-command fallback is unchanged, so ordinary sandboxed commands still run — what vanishes is the explicit allowlist. Switching models mid-thread flips this on or off. Compounding it, the guardian circuit breaker drops both denial limits to **one** rather than three consecutive or ten in fifty — but only for a model whose `model_specialty` is `"cyber"`, not for a slug that merely appears in managed `auto_review.ignore_rules`. Allow-rule stripping covers both groups; the one-denial breaker covers only the first.

### apply_patch

- Patches are intercepted from the shell before execution. A raw patch without the wrapper gets `patch detected without explicit call to apply_patch...`.
- The patch grammar is checked and every target chunk is verified against the real filesystem before any write; failure aborts the whole patch atomically.
- Context matching is fuzzy (four passes down to Unicode punctuation normalization) and applies without telling the model its context lines were inexact.
- Writes outside writable roots hit a safety gate: prompt, or `patch rejected: writing outside of the project; rejected by user approval settings`.
- A patch whose hunks resolve to the same file (`duplicate.txt` and `./duplicate.txt`) is refused whole with `multiple operations target {path}`; nothing is written. Separately, when an otherwise-required sandbox is bypassed, apply_patch runs with `follow_symlinks: false`, so a symlink in any path component is rejected — closing a post-verification path swap.

### A second check at exec time (opt-in backend only)

When the zsh-fork/execve-wrapper backend is active, every `exec()` of every binary — including ones launched by scripts — is re-checked against policy using the resolved absolute path; a script cannot launch what its text hid. Denials appear inside the command's own output as `Execution denied: {reason}` with exit 1, and the command's timeout clock pauses while an approval prompt is pending. This backend requires Unix, `shell_zsh_fork` (under development, default off), `unified_exec_zsh_fork` (`Stage::Removed` with `default_enabled: true`, but still a live compatibility gate — `UnifiedExecShellMode::for_session` ANDs `ShellTool`, `UnifiedExec`, `ShellZshFork` and `UnifiedExecZshFork`, and a regression test asserts that disabling either zsh-fork flag forces Direct mode), the user's shell configured as zsh, and resolvable wrapper binaries. In a default configuration it is NOT active — there the OS sandbox applies its policy once at spawn (inherited by children at the kernel level) with no per-exec re-evaluation against the command-classification engine.

## 3. How execution is confined

- **Sandbox modes**: `read-only` / `workspace-write` (cwd + declared roots + tmp) / `danger-full-access` / external (delegated to a container). Enforced by transparent argv rewriting: macOS Seatbelt (deny-by-default profile), Linux bwrap mount namespace + seccomp (network syscalls → EPERM), Windows restricted token + firewall filters — when the Windows sandbox backend is actually the one running.
- **Windows does not refuse to run unsandboxed — it degrades.** The Windows sandbox backend's feature is flagged at stage `Removed` with `default_enabled: false`, so a mainline Windows build has no sandbox backend to construct in the first place; the degrade path is the normal one, not an edge case triggered by some failure. In that state the harness downgrades the default built-in profile from workspace-write to read-only and pushes every command that no exec-policy rule matched to prompt — or to `Decision::Forbidden` under `never`. The trigger, `profile_has_managed_filesystem_restrictions`, requires a codex-managed profile with a restricted filesystem and no full-disk write access — which is what the downgraded read-only profile is — so `danger-full-access` and externally-enforced profiles do not arm it, and an explicit exec-policy allow still bypasses the sandbox. The known-safe carve-out that used to let inspection commands run unjailed there was deleted along with the safelist module. Separately, the `anyhow::bail!` errors the Windows sandbox crate raises (for example, refusing to build a sandbox for a profile that demands full-disk write access it cannot enforce) fire during sandbox construction, before any question of running a command arises. They are provisioning failures, not exec-time refusals — reading one as "Windows blocked this command" is a category error; it blocked building the jail, not the command.
- Env markers are partial: `CODEX_SANDBOX_NETWORK_DISABLED=1` is set on every platform exactly when the network policy is restricted; `CODEX_SANDBOX=seatbelt` exists only under macOS Seatbelt (its sole value) — Linux and Windows sandboxes set no backend marker, so its absence proves nothing.
- **Protected metadata**: `.git`, `.agents`, `.codex` are carved out of writable roots — hooks/config self-escalation is blocked. Enforcement comes from one shared list (`PROTECTED_METADATA_PATH_NAMES`) rendered by all three backends, and they are not equivalent. **macOS:** per-name Seatbelt deny regexes for every writable root, covering paths that do not yet exist, plus `deny file-write-unlink` on the writable directory roots themselves and on every directory ancestor of a protected path — so renaming or deleting a writable directory root fails with a bare `Operation not permitted` that looks like a filesystem error rather than a policy decision. **Linux:** a synthetic empty read-only directory mount for each *missing* protected path, plus a watcher that deletes protected paths created mid-run and forces exit 1 with `sandbox blocked creation of protected workspace metadata path …`. Because that synthetic `.git` looks like a checkout root, `ls -a` inside the jail can show a `.git` that does not exist on the host — codex's own project-root discovery now requires a `HEAD` file inside the `.git` directory before treating it as repository metadata, and anything you write that infers "this is a repo root" should do the same. **Windows:** real deny ACEs, but only when the sandbox backend is enabled, which is not the shipped default. Skipping a nonexistent sandbox entry is one backend's behavior, not the cross-platform rule.
- **macOS: a symlinked workspace path fails sandbox construction outright.** If any component of a writable root below the top level is a symlink, sandbox setup returns `writable root {} contains symlink component {}; symlinked writable roots are not supported`. Only top-level system aliases (`/tmp -> /private/tmp`) are resolved; deeper components are deliberately not followed, because following them would turn a path check into a new authority grant. It reaches the model as a command failure, not a denial. A workspace under a symlinked home or a symlinked repo checkout trips it.
- **macOS: restricted sandboxes lose the preferences service.** The Seatbelt preferences policy section is appended only when the filesystem policy has full disk read access. Under read-only or workspace-write, `defaults read` and CFPreferences lookups fail even for plists you could otherwise read directly.
- **Linux: the jail also drops capabilities and unshares IPC.** Both bwrap launch modes pass `--cap-drop ALL`. Capability-dependent binaries (`ping` raw sockets, setcap-dependent tools) and cross-boundary System V IPC fail with ordinary EPERM/ENOENT — no codex-branded denial, no retry-unsandboxed prompt.
- **Linux: the sandbox runs as PID 1.** bwrap is launched with `--as-pid-1` (falling back to the bundled bwrap when the system version lacks the flag), so the command runs as a child of that PID 1, which forwards signals and reaps exited descendants — the Linux counterpart to the Windows Job Object in this section.
- **A local HTTP/proxy request abandoned while its network-approval decision is pending cancels the owning command — when there is one.** An execution token exists only for an attributed owning call; where it does, that execution is cancelled and the model receives `Network request disconnected after {elapsed_ms} ms, before approval could complete`. The disconnect metadata explicitly does not cancel the approval reviewer or change its eventual decision, so the reviewer may still finish independently. That string means "the request went away", not "denied".
- **Network** is proxy-mediated and fail-closed; a blocked host surfaces as `Network access to "{host}" is blocked by policy.` An allowlist entry that is an explicit IP literal or the literal `localhost` now lets loopback/private destinations through; without such an entry, loopback and private ranges are still blocked unconditionally regardless of the rest of the allowlist.
- **Denial detection is keyword-based, and the list is exactly seven terms**: `operation not permitted`, `permission denied`, `read-only file system`, `seccomp`, `sandbox`, `landlock`, `failed to write file`. Alongside the keyword match, a small set of exit codes (`2`, `126`, `127`) triggers a quick-reject path on its own, and on Linux a process terminated by `SIGSYS` is treated as a sandbox denial on its own too. Nonzero exit plus any of the above is classified as a sandbox denial — which can false-positive: a command that legitimately prints "permission denied" as ordinary output may be treated as sandbox-blocked.
- **The escalation loop**: a classified sandbox denial may earn exactly one approval-gated retry without the sandbox ("command failed; retry without sandbox?"). Never under `never` — zero exceptions. Not under `on-request` either, except two prompt-gated escape hatches: apply_patch may prompt for an unsandboxed retry, and a denial attributable to an active managed-network policy may prompt for re-adjudication (staying inside the OS jail when deny-read restrictions exist). Separately, any request that asks for escalated sandbox permissions — and any approval retry — bypasses extension approval contributors and gets a full synchronous Guardian review (§2). The model cannot trigger this retry and cannot tell it happened: on approval it just sees the second run's success.
- **Limits, shell exec**: default timeout 10 s (process group SIGKILLed, exit forced to 124, partial output kept). stdout, stderr, and the "aggregate" combined view are not three independent budgets — all three are capped against the same 1 MiB constant; aggregate is a different accounting path over that same limit, not a bigger one. Under contention the split is uneven: stdout gets a third of the remaining budget, stderr gets the other two-thirds.
- **Limits, unified interactive exec**: a call yields after its wait window and can return a process id while the process keeps running. Initial exec waits 10 s by default. A caller may request a longer per-poll wait for `write_stdin` polling, configurable up to 300 s by default. Separately: the poll argument's own default is 250 ms, and an empty poll (nothing new to return) is clamped up to a 5 s floor regardless of the requested value — 5 s is a lower bound on empty polls, not a default wait time. A distinct constant caps non-empty writes at 30 s — a bound the previous version of this reference omitted entirely. These are wait bounds, not process lifetimes.
- **Windows process containment**: pipe, ConPTY, and sandboxed child processes are placed in a Job Object, so a cancel, a timeout, or an explicit stop now brings down the whole process tree together. This weakens the "background processes may still run" caveat in §5 specifically on Windows — see the note there.
- **Headless runs** (`codex exec`) default the approval policy to never, so would-be prompts normally become deterministic rejections. When the resolved approvals reviewer is AutoReview, the headless never override may be removed and the configured approval policy rebuilt.
- **`--worktree` relocates a headless run before its config is loaded.** The flag is exec-only. `codex exec` and `codex exec fork` accept it; `codex exec resume` bails with `` `--worktree` cannot resume an existing session; use `codex exec fork --worktree` ``, `codex exec review` with `` `--worktree` is not supported for code review ``, and every other subcommand — the bare interactive TUI included — with `` `--worktree` currently supports only `codex exec` and `codex exec fork` ``. `codex exec` re-checks the resume and review cases itself and additionally refuses `--ignore-user-config`, `--ephemeral`, and a default environment that is remote (`--worktree requires local execution`). The `worktrees` feature is Experimental and default-off, and the gate config is built with `ignore_project_config: true`, so a project `.codex/config.toml` cannot turn it on — only user config or a CLI override (`--enable worktrees`, or the `-c` it folds into). Allocation is deliberately host-scoped rather than session-scoped: bootstrap config is reloaded with no cwd, no `-c` overrides and default loader overrides, and only `desktop.git-worktree-root` is taken from it (default `<codex_home>/worktrees`), with `auto_cleanup_enabled` forced to `false`. The worktree crate is a dependency of `codex-exec` alone, exposes create, list, bind_thread and owner with no public removal, and nothing in codex-rs reads `auto_cleanup_enabled` or `keep_count` — so nothing in codex-rs reclaims a CLI checkout. The checkout itself is `git worktree add --detach --no-checkout` followed by `reset --hard <HEAD sha>` into `<root>/<4-hex bucket>/<repo>`, preserving your path relative to the repository root — detached, `branch: None`, and carrying committed state only. Ordering matters twice: relative `--add-dir` paths are rebased against the *original* cwd before the swap, and the session's bootstrap config is loaded *after* it, so the project-config layer and the AGENTS.md chain both anchor on the new cwd and resolve inside the checkout. Trust is the exception: the trust resolver walks a linked worktree's `.git` file back to its main checkout, so the source repository's trust decision still governs the run. Once `thread/start` returns, the thread id is written into the checkout's metadata.
- Environment hardening strips all `LD_*`/`DYLD_*` variables and clears env for internal helpers — preload tricks and inherited secrets silently vanish.
- A second, named list (`NON_INHERITABLE_ENV_VARS`) removes five variables from model-reachable children: `CODEX_EXEC_SERVER_NOISE_AUTH_TOKEN`, `NODE_REPL_AUTH_TOKEN`, and the three `OPENAI_*` workload-identity variables. It is applied at the exec-server client transport, shell snapshots, both hook runners, the shell-escalation server, the code-mode host connection, the PowerShell parser probe and every git subprocess, and it removes names the command itself set as explicit overrides — so a shell-environment policy cannot put them back. The source scopes this as launch-context hygiene, explicitly *not* a filesystem security boundary for the referenced identity-token file.

## 4. How results are shaped on the way back

- **Double truncation**: tool output is middle-cut to the model's token budget (`…{N} tokens truncated…` marker, head and tail kept), then re-truncated again when recorded into history — oversized output never survives into later prompts.
- **An MCP result is budgeted five separate ways, and only two of them are that double truncation.** The effective policy is captured from the same config snapshot the call executed under: the per-tool `[mcp_servers.<server>.tools.<tool>].output_token_limit` when one is set, otherwise the model's own truncation policy. (1) The model-facing function output is middle-cut at that policy times 1.2 — the 20% serialization allowance the config field is documented against. (2) The history copy carries that same budget forward as a `fallback_token_limit_override` and is cut at it when the item is recorded, including on resume, so for an MCP result the second cut re-applies the first cut's budget rather than costing anything further. (3) `PostToolUse` hooks receive the whole serialized `CallToolResult`, `_meta` included, uncut. (4) A Code Mode script receives the result serialized *without* `_meta`, which is deliberately withheld from Code Mode, and uncut by the tool's budget — what the script finally yields is instead re-cut at Code Mode's own script-output budget, so a per-tool limit does not bound a nested MCP call at all. (5) The completion event the app-server rebuilds `ThreadItem::McpToolCall` from is capped by *bytes*, not tokens, at the same 1 MiB `DEFAULT_OUTPUT_BYTES_CAP` the exec pipeline uses; over that the whole result is collapsed to a text preview of its own serialization with `structured_content` and `_meta` dropped to `None`, so the persisted transcript can be lossier and structurally poorer than what the model read. Overlapping budgets combine by `min` — when a plugin-declared tool config and the operator's config policy for that plugin both name a limit, the stricter one wins — and that merge moves the budget only, never the tool's approval mode.
- **An extension can rewrite an MCP result before any of those five paths sees it.** Every registered tool-lifecycle contributor is handed `&mut CallToolResult` — content, structured content and `_meta` — after `tools/call` returns and before modality sanitization, the client completion event, and the model-facing output. What the contributor leaves behind is authoritative for everything downstream; the server's actual response is not recoverable from any later path.
- **The two embedder-driven MCP requests hand the *client* a structured error the model never sees.** `mcpServer/tool/call` and `mcpServer/resource/read` funnel their failures through one mapper — the app-server's only structural read of a server error: an rmcp `ServiceError::McpError`, still downcastable through the `.with_context()` the connection manager wraps it in, comes back verbatim with the server's own numeric `code`, `message` and `data`; everything else collapses to `-32603` carrying `{error:#}` and no `data`, which is where a client-side timeout, an unknown server, and a tool excluded by codex's own `[mcp_servers.<name>]` `enabled_tools`/`disabled_tools` filter all land. On `resource/read` that code is not a reliable "the server failed" signal — two codex-side steps land on it too, the config load that precedes the threadless read and the deserialization of an *already successful* read into `McpResourceReadResponse` — whereas `tool/call`'s own pre-mapper failures (bad thread id, thread not found, direct input refused) are `-32600` instead.
- **Framing**: every exec result is wrapped with `Exit code: N`, `Wall time: N seconds`, and `Output:` headers; timeouts prepend `command timed out after {N} milliseconds`.
- **No output scrubbing happens at this stage.** Codex ships a credential vault (`codex-secrets`, primarily an OS-keyring-backed store) and a regex-based secret sanitizer, but the sanitizer has exactly three call sites — OAuth token handling, memory-writing, and auth storage — and none of them sit in the exec or tool-output pipeline. Nothing in this result-shaping stage redacts secrets out of command output on the way back to the model.
- **PostToolUse hooks** can retroactively reject a completed result (side effects already happened; the model sees the hook's feedback instead of the real output), swap a successful result's model-visible text for the hook's feedback message (the original output is retained internally; hooks cannot forge an arbitrary structured tool response), or inject extra context as separate developer-role messages.
- **Hook output over ~2,500 tokens** is spilled to a file; the visible text ends with `Full hook output saved to: {path}` — the agent can read it back with file tools.
- **History repair**: before every request the harness synthesizes missing tool outputs, drops orphans, and silently trims old assistant text to token budgets — with no marker. Separately, when the model's declared modalities don't support image or audio input, unsupported content is proactively replaced with placeholder text ("image content omitted because you do not support image input" / "audio content omitted because you do not support audio input") — this is unconditional on modality, not a reaction to an API error. An actual API rejection of an invalid image used to trigger a silent retry with the image swapped for literal "Invalid image" text; that retry-and-rewrite path has been removed — a rejected image now ends the turn immediately with a user-visible error ("Invalid image in your last message. Please remove it and try again."), no silent retry, no history rewrite.

### Rejection-string vocabulary

Observed internal UI/test strings — not a stable API; frontends may reword them, and the list is not exhaustive.

Match on the literal fragment between placeholders, never on the whole templated string — the placeholder names shown here are for readability and don't always match the source's internal field names. For example, this document writes `unsupported call: {tool}`, but the source's own template uses a differently-named placeholder internally; grepping the fragment before the placeholder (`unsupported call: `) still finds it, grepping the literal string with `{tool}` in it does not. The same trap applies to `` `{command}` rejected: policy forbids commands starting with `{prefix}` `` (match on `rejected: policy forbids commands starting with`), `aborted by user after {secs}s` (match on `aborted by user after`), `command timed out after {N} milliseconds` (match on `command timed out after`), and `Network access to "{host}" is blocked by policy.` (match on `is blocked by policy`).

Denial reasons are propagated rather than fixed: a denial carries a reason string identifying its source — e.g. `PermissionRequest hook denied approval` (a hook's default when it supplies no message; `rejected by configuration` now appears **only** where a hook denies by proposing a network-policy deny-amendment), `rejected by user` (human), the guardian's full risk rationale, `approval request aborted` (abort), `approval request failed` (transport failure) — so read the reason to see which layer denied instead of assuming one generic string. The list of reasons is open-ended; callers supply the text.

| The agent sees | What actually happened |
|---|---|
| `exec command rejected by user` | The denial carried the exact reason `rejected by user` — in practice a human declining or aborting through the client. Only the exact reason string `rejected by user` is rewritten this way; a hook, guardian or failed client reason passes through verbatim |
| `patch rejected by user` | Same, for apply_patch |
| `write_stdin rejected: {reason}` | Terminal-input review refused a write; nothing reached the process. Only under `write_stdin_approval` (default off). Match on `write_stdin rejected: ` — the wrapper is the stable part, the reason is propagated from whichever layer refused, and is *not* rewritten into the exec/patch form |
| `` …cannot enforce the current … restrictions; start a new terminal `` | The running terminal cannot enforce a denied-read or environment-owned network restriction that is in force now. No reviewer ran and none would help — an approval cannot retrofit a sandbox onto a live process. Match on `restrictions; start a new terminal` |
| `terminal input contains a NUL byte and cannot be reviewed safely` | Manual approval shell-quotes the input and cannot preserve a NUL, so the write is refused rather than reviewed |
| `terminal input and permission details are too large to review safely…` | The formatted action plus its reason exceeded 8,000 bytes, or the formatter truncated the action. Refused whole — no unreviewed tail is written. Match on `too large to review safely` |
| `write_stdin approval failed: {err}` | The write_stdin approval ended in a harness error rather than a decision — an abort delivered through the approval machinery arrives here as `TurnAborted`. Match on `write_stdin approval failed: ` |
| `` …rejected: policy forbids commands starting with… `` | A forbidden prefix rule matched; command never spawned |
| `` …rejected: rm -f style commands are not permitted. Use a safer approach `` | Dangerous-rm heuristic matched (env/trap/pipeline/control-flow/substitution/nested-shell aware); command never spawned |
| `approval required by policy, but AskForApproval is set to Never` | Prompt suppressed by policy; nothing was asked |
| `approval required by policy, but AskForApproval::Granular.sandbox_approval is false` | Granular policy has sandbox-escalation prompts turned off; nothing was asked |
| `approval required by policy rule, but AskForApproval::Granular.rules is false` | Granular policy has rule-based prompts turned off; nothing was asked. Note the extra `rule` — this row alone says `policy rule`, and a grep written against the other two rows' wording misses it |
| `approval policy is …; reject command — you cannot ask for escalated permissions…` | The agent requested escalation in a mode that forbids it |
| `This action was rejected due to unacceptable risk.` | Guardian LLM denied it; no human was asked |
| `Command blocked by PreToolUse hook: …` (a `Bash`/`apply_patch` call carrying a command) or `Tool call blocked by PreToolUse hook: …` (every other tool) | A configured hook vetoed the call pre-execution |
| `Execution denied: …` (inside command output, exit 1) | Per-exec policy check blocked a binary launch (zsh-fork backend only) |
| `unsupported call: {tool}` | The tool doesn't exist in this step's tool list |
| `user rejected MCP tool call` | MCP approval denied; the server was never contacted |
| `MCP tool call blocked by app configuration` | App-tool policy disabled that `codex_apps` tool; the server was never contacted and nobody was asked |
| `` MCP tool `{server}/{tool}` is not available to the model `` | The call resolved to no MCP binding for that server/tool in this step. Nothing was denied; a server still starting behind a cached catalog is one cause among several |
| `MCP tool call requires approval, but approval policy is never` | An MCP call needed approval under `never` while the permission profile is Managed without full-disk write. Under a Disabled or External profile, or a Managed one with full-disk write, the same call is auto-approved instead |
| `user cancelled MCP tool call` | An MCP approval was aborted; converted to a tool result rather than a turn teardown |
| Output containing `operation not permitted` / `permission denied` / `read-only file system` / `seccomp` / `sandbox` / `landlock` / `failed to write file` | OS sandbox denial, classified by keyword match and surfaced as-is (no retry was offered) |
| `command failed inside sandbox with exit code {N}` | Sandbox denial with empty output |
| `patch detected without explicit call to apply_patch…` | A raw patch was sent outside the `apply_patch` wrapper; resend it as a real `apply_patch` call |
| `patch rejected: writing outside of the project; rejected by user approval settings` | apply_patch's target path fell outside the writable roots |
| `Network request disconnected after {ms} ms, before approval could complete` | A local HTTP/proxy request gave up while its approval was pending; an attributed owning execution is cancelled, the reviewer is not — nobody denied it |
| `multiple operations target {path}` | Two apply_patch hunks resolved to the same file; the whole patch was refused before any write |
| `symlinked writable roots are not supported` | macOS sandbox construction failed on a symlinked writable-root component; nothing ran |
| `Requested timeout of {N}ms was clamped to the minimum of {M}ms.` | `wait_agent` lengthened a too-short timeout rather than failing |
| `` Codex delegates require approval policy `never` `` | A review-mode or Guardian delegate was handed a prompt-capable config and refused to start |
| `environment command policy cannot contain allow rules` | An environment's exec-policy overlay tried to widen rather than tighten |
| `approval_policy = "untrusted" is no longer supported; remove this setting` | Config load failed; the policy is internal-only now |

This table is longer than SKILL.md's triage version because it also carries the two Granular-specific strings and the apply_patch-specific strings verbatim, alongside the keyword-level view SKILL.md needs for fast matching.

Two things about how these actually arrive, both observed in a live `codex exec` run rather than read out of the source:

**Policy rejections are nested inside a wrapper, OS denials are not.** A rejection reaches the model wrapped in the spawn error that carried it — `` exec_command failed: CreateProcess { message: "Rejected(\"approval required by policy, but AskForApproval is set to Never\")" } `` — so the reason string is a substring of a Rust-debug-formatted blob, never a line of its own. The wrapper does **not** echo the command you sent; whether the command appears anywhere depends on which gate wrote the reason it carries — a `prompt` prefix rule rejected under `never` contributes the bare constant, while a heuristic-driven `Forbidden` — the stock forced-rm case under `never` — and `forbidden` prefix rules render the command in backticks inside the reason. The whole message is middle-truncated at 900 bytes — a byte cap, since `truncate_middle_chars` compares `s.len()` against it — so a long debug payload loses its middle and can cut the reason string itself in half. An OS-jail denial gets no wrapper at all: it is the command's own stderr, verbatim (`touch: /tmp/x: Operation not permitted`). That asymmetry is why keyword matching beats line matching, and why sandbox denials are the ones most easily mistaken for ordinary tool errors.

**The forced-rm sentence arrives in two forms, and a `prompt` rule suppresses both.** When the heuristic drives the decision to `Forbidden` — which is what `never` does to any positively identified forced-rm — the reason is built by `derive_forbidden_reason` and reads `` `rm -rf /tmp/x` rejected: rm -f style commands are not permitted. Use a safer approach ``, command included. When a heuristic-driven `Prompt` is instead rejected by a `Granular` policy, `derive_rejected_prompt_reason` *substitutes* the same sentence for the fallback reason, bare: no `rejected:` prefix and no command. Neither form appears when a policy `prompt` prefix rule is what produced the `Prompt` decision — that branch returns the bare policy constant without ever consulting the dangerous-command match. So a host whose rules file prompts on `rm` sees `approval required by policy, but AskForApproval is set to Never` for a `rm -rf` under `never`, while a host without such a rule sees the command-echoing form. Shell wrapping is not the discriminator: `bash`, `zsh` and `sh` invoked with `-c` or `-lc` are parsed and the inner `rm` is still seen. Treat the rm sentence as a signal that a forced-rm was positively identified *and* that no prompt rule pre-empted it.

## 5. Cross-cutting loops

- **Stream retry, silent to the model**: transport/API errors replay with exponential backoff, then one permanent WebSocket→HTTPS fallback (websocket-capable providers only). One case escapes that bound entirely: with the stable, default-on `unbounded_connection_retries` feature, a user-facing sampling request whose error is `ConnectionFailed` sleeps a doubling `connection_retry_delay` (clamped to `MAX_CONNECTION_RETRY_DELAY`) and retries **with no ceiling**, bypassing `max_retries` and the transport-fallback path and emitting only a `Reconnecting... waiting for network` stream-error notice. Internal session sources and Amazon Bedrock providers are excluded and keep the bounded path. Retryability is a typed property of the error detail rather than a policy applied to all failures: `MisalignmentPolicyViolation` and `CyberPolicy` sit in the non-retryable arm alongside `RefreshTokenFailed` and `UsageLimitReached`, and the reference client treats a misalignment verdict as terminal for the thread — it clears the input queue, disables the composer under `Chat stopped as a precaution`, and accepts only interrupt, terminal cleanup, turn-context override, config reload, skill listing and rename thereafter. Also permanent: a token refresh that fails with HTTP 400 and code `invalid_grant` is classified permanent (other 400s stay transient), cached against the current credential snapshot so later refreshes fail with no network call, and surfaces as the non-retryable `RefreshTokenFailed`. Each retry rebuilds the prompt from current history — the model observes nothing, though the user's frontend does receive warning/stream-error events (including a one-time "Falling back from WebSockets to HTTPS transport" notice).
- **Auto-compaction rewrites memory**: at token thresholds (or when the model calls the context-window tool — which is only a request), the harness has the model summarize its own progress, then replaces the working history with that summary plus freshly re-injected permissions/environment/AGENTS.md. Feature-enabled retained items can survive the boundary too: remote compaction V2 with `retain_client_developer_messages` (under development, default off) keeps client-authored developer messages. In the new window, prior work is introduced as "Another language model started to solve this problem and produced a summary…" — the agent's own past presented as a stranger's, all intermediate tool traffic gone. On overflow, oldest items are silently dropped one at a time. An opt-in refinement exists, gated behind a token-budget feature flag and an explicit configured prompt: a fallback phase can fire before the real rollover, reserving extra buffer tokens and injecting the configured prompt exactly once as a bare message — one chance for the model to write down state before compaction actually replaces history.
- **Interruption**: aborted tool calls become synthetic outputs (`aborted by user after {secs}s`), and the next turn opens with a `<turn_aborted>` marker warning that aborted commands may have partially executed and background processes may still run. On Windows this is now weaker than it sounds: pipe/ConPTY/sandboxed children live inside a Job Object (§3), so a cancel or timeout usually takes the whole process tree down with it rather than leaving orphans running. Interruption is also a first-class hook event: a configured `Interrupt` hook fires on that path against the last executing step's discovery, skipping subagent sessions, with no veto capability and a parsed output of nothing but a system message, on the same 1 s default / 3 s cap as `SessionEnd` — and executor hook sources from that step are merged in, so a turn with no local `Interrupt` hook still runs the executor's.
- **Stop hooks — the agent may not be allowed to stop**: when the model ends its turn, a configured stop hook can reject the stop; its reason is injected as a new prompt and sampling resumes. Hook timeouts fail open (a hung hook never blocks). A hook that exits normally without reading all of its stdin is tolerated too: the resulting broken pipe is ignored, and the harness uses the hook's actual exit code and output rather than treating the broken pipe itself as a failure.
- **Session teardown hooks**: a `SessionEnd` hook runs fire-and-forget during session shutdown, after exec/MCP/code-mode teardown — it has no veto capability at all, defaults to a 1 s timeout hard-capped at 3 s, and fires only for the root session, not subagent/`ThreadSpawn` sessions. Its `async: true` config flag is currently a no-op — it still runs synchronously.
- **A hook handler is not necessarily a shell command.** `HookHandlerConfig` also accepts `type = "mcp_tool"`, which calls a tool on an already-connected MCP server instead of spawning a process; two further types, `prompt` and `agent`, parse but are dropped at load with `prompt hooks are not supported yet` / `agent hooks are not supported yet`. An MCP handler names a raw `server`/`tool` pair plus an `input` template, a `timeout` and a `statusMessage`. The `input` map must be representable as TOML — a `null` anywhere inside it fails config load with `MCP hook input must be representable as TOML` — because the normalized handler, template included, is what the trust hash covers: editing a template silently stops the hook firing exactly as editing a command does. The template is expanded recursively against the hook event JSON. `${field.nested}` walks dotted **object** keys only; a placeholder spanning the entire string returns the referenced value with its JSON type intact, an embedded placeholder stringifies it, and an unresolvable path fails the whole hook with `` hook input placeholder `${…}` was not found `` rather than passing the literal through. Empty `server` or `tool` is dropped at load, and so is any `SessionEnd` MCP hook, with `SessionEnd MCP hooks are not supported`. The timeout defaults to 600 s; only `Interrupt` clamps it to the SessionEnd 1 s / 3 s constants, because a `SessionEnd` MCP hook is dropped before it is ever normalized.
- **What an MCP hook can do, and what stops gating it.** A hook from a local source runs synchronously, so it can block, rewrite a tool's input or inject context exactly like a command hook — but only through JSON in the tool's returned text, because the runner reports exit code 0 on success and *no* exit code on failure, and never writes stderr. The exit-code-2-plus-stderr blocking convention is therefore unreachable from an MCP handler, and any failure — transport, timeout, or an MCP result marked `isError`, which surfaces as `MCP tool returned an error: {text}` — is a `Failed` run that fails open. The call itself is issued straight at the server connection rather than through the path the model's own MCP calls take, so no approval prompt, no Guardian review and no `codex_apps` approval-mode evaluation apply to it, and it produces no MCP tool call in the transcript — only a hook run. What still applies is the server side: an unknown name fails with `unknown MCP server '{server}'`, the server's own config-level tool filter (`enabled_tools`/`disabled_tools`) with `tool '{tool}' is disabled for MCP server '{server}'`, the effective timeout is the smaller of the hook's timeout and the server's configured tool timeout, and readiness is not waited for — a hook aimed at a server still inside its startup grace fails with `MCP server '{server}' is not connected`. Executor-scoped MCP hooks are forced async and so cannot apply control effects at all.
- **Mid-stream preemption**: queued user input can cut the model's response short at an item boundary and land between tool rounds unbidden.
- **Externally started turns**: where app-server is configured with a durable queue store, a detached watcher polls SQLite's `PRAGMA data_version` on one stable connection every 10 seconds, so a queued user message committed by a *different process* is seen. For any thread this process has already loaded and is not currently running, that message is dispatched via `start_turn_if_idle` and starts a real turn with no request from the connected client — the only client-facing signal is a `ThreadQueueChanged` event, and a `NotSubmitted` outcome is logged as a warning and nothing more. Work that begins with no submission of yours is worth checking against the durable queue before blaming the model.
- **Budget hard stops**: once the cross-thread budget is exhausted, turns terminate with a hard error regardless of task state.
- **Codex delegates (review mode, guardian reviewers)**: a delegate is refused outright unless its approval policy is `never` — anything prompt-capable fails with `` Codex delegates require approval policy `never` `` — after which the policy is pinned. Review mode runs in exactly such a delegate (web search and collaboration tools disabled, and a rubric that requests findings JSON). The output is parsed best-effort as JSON, with plain-text fallback.

## 6. Subsystems the operational layer only summarizes

SKILL.md's Layer 0 and "What you actually have by default" sections give the operational summary for the subsystems below — how to tell they're active, and the one or two things worth doing differently. This section is the mechanism behind that summary, organized by subsystem rather than by pipeline stage.

### Code mode

In code mode the model writes JavaScript instead of making tool calls. Code mode executes in a separate host process — the codex process itself contains no V8. Inside the host the script is evaluated as an async ES module in a fresh V8 isolate — no Node, no filesystem, no network, and `console` is deleted from the global object. Nested tools are exposed as `tools.foo(args)` promises, and a companion `wait` tool resumes a suspended cell. Nested calls dispatch through the same router as direct calls, so every gate in this document is applied to each one individually; a denied or failed nested call surfaces to the script as a **rejected promise it can catch within the same turn**, rather than as a tool result the model reads on the next turn. Runaway scripts are stopped by V8 isolate termination, not an OS timeout. In `CodeModeOnly` specifically, tools outside `exec`/`wait` are hidden from the model-visible menu outright rather than routed through the script, except those explicitly marked direct-model-only or excluded by namespace. The host binary is resolved by path candidate rather than by probe (bundled `codex-resources/codex-code-mode-host`, then the package bin directory, the standalone release directory, or the current executable's directory); a candidate path is returned even when nothing is there, availability is a later `is_file()` check, and the process is spawned lazily — a missing host does *not* abort startup. Fallback is asymmetric: ordinary `CodeMode` with an unavailable host and `disable_in_process_fallback` unset resolves to `ToolMode::Direct`, while `CodeModeOnly` never falls back and fails closed, surfacing the host failure to the model as tool output from the `exec` call. The caller sees one warning either way, `Falling back to direct tools` or `Code mode will fail closed`. Note also that the `CodeModeOnly` hiding rule is narrower than "everything but `exec` and `wait`": it drops a tool only when that tool is *available in code mode*, so `DirectModelOnly`, `DeferredModelOnly` and `Hidden` tools survive, and hosted tool specs are appended after the filter runs (`hosted_model_tool_specs` contributes only the hosted `web_search` tool at this pin, and nothing at all on a responses-lite model or in a Guardian-reviewer session). What puts a model into code mode is the catalog reading order described in Layer 0 above; how to recognize it mid-session is in SKILL.md.

### Subagents and agent mail

Two parallel subagent systems exist, and the resolution order decides which one you get: the `multi_agent_v2` feature (Stable, default **off**) wins outright, then the model catalog's own version, then the `multi_agent` feature (Stable, default on) yields V1. V1 registers `spawn_agent`, `wait_agent`, `close_agent`, `resume_agent` and `send_input`, so it is what an ordinary session gets, limited by a spawn depth that defaults to 1 — though on a search-capable, namespace-capable model those five register as `Deferred` rather than direct, invisible until tool search surfaces them. V2 registers `spawn_agent`, `send_message`, `followup_task`, `interrupt_agent` and `list_agents`, plus `wait_agent` only when `multi_agent_v2.wait_agent_enabled` is set, and exposes them `DirectModelOnly` under `non_code_mode_only`. `send_input` is the "mail" half of the V1 set: it delivers new text to an already-running subagent rather than spawning a new one; `send_message` and `followup_task` are its V2 counterparts. The two versions are not drop-in replacements for each other:

| | V1 | V2 |
|---|---|---|
| target | UUID only | task paths or UUID |
| fork argument | `fork_context` | `fork_turns` — `fork_context` is rejected with `fork_context is not supported in MultiAgentV2; use fork_turns instead` |
| spawn result | `agent_id` | `task_name` |
| messaging | `send_input` (returns a `submission_id`, supports `interrupt`) | `send_message` queues only; `followup_task` triggers a turn. Both return empty success text |
| wait | waits for the agent's final status, returns `{status, timed_out}` | waits for mailbox activity, returns `{message, timed_out}` |

Neither V2 messaging op waits for the target's turn to finish, and `followup_task` cannot target the root agent (`Follow-up tasks can't target the root agent`). Two V2 config flags change what the model sees: `non_code_mode_only` registers the collaboration tools `DirectModelOnly` (still ordinary model tools in a `code_mode_only` session, but not callable from nested code mode) rather than `Direct`; `hide_spawn_agent_metadata` suppresses the inherited-model guidance text, removes `service_tier` from the spawn schema, and reduces a successful spawn result from `{task_name, nickname}` to `{task_name}`. It does *not* remove `model` / `reasoning_effort` — those follow `expose_spawn_agent_model_overrides`. Beyond that:

- **The V2 delegation posture is catalog-supplied, and an empty string is a delete, not a reset.** `effective_multi_agent_mode` returns `None` outright unless the resolved version is V2. Under V2 it resolves in order: config `multi_agent_v2.multi_agent_mode_hint_text`, else the catalog's `multi_agent.mode.hint_text`, else — with no hint text from either — the catalog's `multi_agent.mode.proactive` when the effective reasoning effort is `Ultra` and `multi_agent.mode.explicit` otherwise, else the built-in `Proactive` / `ExplicitRequestOnly`. Any custom string is truncated to 400 tokens (`MULTI_AGENT_MODE_MAX_TOKENS`) before it renders, and an empty one renders nothing at all: `MultiAgentModeInstructions::from_mode` returns `None` for `Custom("")`, so the section disappears instead of falling back to the built-in text. The resolver also yields `None` for internal sessions and for every subagent source except `ThreadSpawn`, so a spawned child does not necessarily read the delegation posture its parent reads. One exception lives in the renderer rather than the resolver: wherever the mode is `None` — V1, internal and non-`ThreadSpawn` subagents alike — the world-state section still emits a bare `ExplicitRequestOnly` message if the previous snapshot said `Proactive` or could not be read at all, so "no mode" is not the same as "no message".
- Depth-1 limits how many levels deep a spawn chain can go, not how many siblings exist at any one level — width isn't limited the same way.
- Codex ships built-in agent roles, but right now they're placeholders rather than active behavior: one shipped role's config is an empty file, and another exists in source but is commented out of the built-in role list — neither currently changes anything by existing. What is fully live is the underlying mechanism a user-defined role plugs into: a role carries a closed `AgentRoleOverrides` set — developer instructions, model, reasoning effort, reasoning summary, verbosity, personality, service tier, features and skills — and nothing else, one of which (service tier) is overwritten immediately after the role is applied, see below. Two of those fields are narrower than they look: only a *disable* keyed by the exact feature key `shell_tool`, `apps`, `personality`, `plugins`, `memories` or `request_permissions_tool` is honored (`memory` is not a key at all, and the legacy alias `request_permissions` resolves to a different feature, `ExecPermissionApprovals`, so both are silently dropped), and the skills field only ever removes explicitly selected configured or bundled skills — every other feature toggle a role asks for is silently dropped. Sandbox mode and approval policy are simply not fields on it, and authority is reapplied over the top regardless: `apply_spawn_agent_runtime_overrides` copies the live parent turn's approval policy, approvals reviewer, cwd and permission-profile snapshot onto the child config, its doc comment saying this exists so a child cannot "disagree with its parent about approval policy, cwd, or sandboxing". What *is* free to differ from the parent is everything else the spawn path sets — model, provider, reasoning effort and summary, developer instructions (which V2 replaces wholesale with `multi_agent_v2.subagent_developer_instructions` when configured), personality and skill surface. Service tier is the exception that looks like a field but is not: `apply_spawn_agent_service_tier` runs *after* the role is applied and overwrites whatever the role set with the root thread's current tier, or clears it when the root has none, or clears it when the child's model does not support that tier. A role's `service_tier` therefore parses and then never takes effect, and a live change to the root's tier propagates down the agent tree. Inheritance is exact for authority and for the service tier, and free for nothing else on that list.
- **Guardian review of a subagent reads the ROOT thread as authorization evidence, and that evidence is wider than user messages.** A bounded snapshot of the root thread's history is injected as a `>>> ROOT CONVERSATION START` block ahead of the reviewed transcript, preceded by an instruction that only root *user* messages can authorize actions and that assistant messages are untrusted context. But the snapshot carries three things beyond plain user turns: host-verified `request_user_input` answers attached to their retained function calls, the verified filesystem paths of user-owned skills invoked on the latest root user turn, and an explicit incomplete-evidence marker when retained verified answers are missing or too large — which itself blocks cached fast approval. Skill provenance is load-bearing here: only skills under the user's own Codex / `.agents` roots earn trusted paths, repository skills and symlinks escaping those roots do not, and the trust is matched to the turn rather than inherited forever. Practically: permission the user granted in the root thread after a worker was spawned does reach that worker's review, an answer the user typed into a `request_user_input` prompt counts as authorization, and a worker still cannot manufacture authorization by restating in its own transcript that the user approved something.
- `wait_agent` no longer rejects a too-short timeout — it clamps to a configured minimum and appends `Requested timeout of {N}ms was clamped to the minimum of {M}ms.` to the result. Polling with a 100 ms wait does not buy a 100 ms turnaround.

### Skills delivery

Skills reach the model three ways: the budgeted catalog listing, a `$skill-name` mention that injects the full body as a `<skill>` fragment, and the `skills.list` / `skills.read` tools. An explicit-only executor skill is omitted from `list` but still fetchable through `read`, so the listing is not the full set of what is reachable. Five further mechanics:

- The instructional text that teaches the model how to invoke a skill it just discovered is itself part of the render path and can change independently of the skill's own content — treat its exact phrasing as no more stable than any other string in this document.
- There is one renderer — the `ext/skills` crate — serving several catalog surfaces; the former `core-skills` crate no longer exists, so its budget and warning behavior are the only ones there are. The budget resolves as in §1: a configured `max_context_tokens` capped at 10,000 tokens, else 2% of the resolved context window, else a flat **8,000-character** budget for any surface that passes no window. When two or more catalogs are non-empty they *share* that single budget rather than each getting it. The old "4,000-token tool-call ceiling" no longer exists anywhere.
- When the catalog is over budget, **neither reshape is visible to the agent.** Description-shortening and whole-skill removal do produce warning strings (`Skill descriptions were shortened to fit the skills context budget…` and `Exceeded skills context budget. All skill descriptions were removed and …`), but `warning_message()` is routed to the *client* as an extension warning event, separate from the fragment that becomes model-visible text. The human sees it; the model does not. Skill-locator aliasing to `r0`/`r1` placeholders is unannounced on both sides — the same unmarked pattern as the tool-schema compaction in §1 — but it is not usable as a pressure signal. The renderer builds the absolute catalog and the aliased catalog on every render and compares them on three keys in order: skills included, then description characters truncated, then rendered cost. Aliasing wins the plain tie whenever it is merely cheaper, so it shows up in catalogs that were never near the budget. On the combined path the comparison runs over five candidates — unaliased, plus aliasing the executor, the orchestrator, the host, or all three — so one source catalog can render aliased while another beside it does not. From inside: a short catalog is still evidence of silent incompleteness; an aliased one tells you nothing either way. Enumerate with `skills.list` regardless.
- **`skills.list` and `skills.read` page against the calling turn's response budget, and that budget depends on how you were invoked.** A direct tool call gets `min(512 KiB, 1.2 × the model's tool-output truncation policy)`; a code-mode call gets the flat 512 KiB, because typed results skip host truncation. All nine slugs in the shipped model catalog declare a 10,000-*token* truncation policy at four bytes per token, so a direct page is 48,000 bytes on every one of them — the `bytes`-mode exception the catalog used to carry went with `gpt-5.2`, which is no longer shipped, so check `truncation_policy.mode` rather than assuming a slug is the token-mode one. Code mode is an order of magnitude more per page either way, which is the same `skills.read` costing ten to forty round trips instead of one. `list` pages at 20 skills, drops any entry whose own single-entry response would not fit and any whose authority, package, name or main_resource exceeds 2,048 bytes, and reports both as `Some skills were omitted because their metadata is too large.` in the response's `warnings` array; the cursor encodes the budget as well as the offset, so that warning is emitted once per budget value rather than once per page. Under further pressure `list` shrinks the page one entry at a time, then drops provider warnings, then returns a page with **no skills at all** — warnings only, plus a cursor that resumes at the same offset — and only after that fails with `skills.list response budget leaves no room for discovery warnings` or `skill metadata is too large to list`. `read` binary-searches the largest page that fits, cutting on serialized-JSON and UTF-8 character boundaries, and returns `skills.read response budget leaves no room for contents` when no prefix fits at all. Cursors from both tools are fingerprinted over the value being paged, so a catalog or file that changed under you fails with `cursor is stale; restart from the first page` instead of splicing at a byte offset into different content.
- **An executor-backed `read` continuation may be served from a snapshot taken before the file changed.** One snapshot slot per thread is written only when the authority is executor, more pages remain, and the file is at most 1 MiB. It has no expiry and is not cleared after the final page, and it is overwritten only by another executor read that itself paginates — a single-page read, an oversized read, or any orchestrator read leaves it in place. A continuation hits it only when authority, package, resource, environment and sandbox all match; on a miss the file is re-read and the fingerprint check fires normally. On a hit, file edits are not detected and the stale-cursor check cannot fire, because the fingerprint was taken over the snapshot. This one is not silent: the tool description tells the model `continue the same snapshot while it is cached; omit cursor to read again`. To read a file you have just edited, omit the cursor and start over.

### Image generation

Codex installs an image-generation extension unconditionally in both app-server and mcp-server, but the tool `image_gen.imagegen` survives into the menu only when the `image_generation` feature is on, the account plan is not Free, the provider advertises `image_generation` and `namespace_tools`, the model's input modalities include `Image`, and auth is OpenAI-actor-header or Codex-backend — in practice ChatGPT-family auth on a paid plan. Its output is written to `$CODEX_HOME/generated_images/<session_id>/<call_id>.png` through `LOCAL_FS` with `sandbox: None`, outside the workspace and outside the filesystem jail. On success the model is handed a hint naming the directory and path, unless that hint exceeds 1,024 bytes, in which case it is dropped entirely.

### History and notes (off by default)

With `features.token_budget.use_history_notes_extension` set, an OpenAI model provider, and auth on the Codex backend, the history-notes extension registers namespaced `history.*` and `notes.*` tools at `ToolExposure::DirectModelOnly`. History is read-only and eventually consistent — newly generated items take seconds to appear. The client-side caps this reference used to list (100 windows, 20 items, 2,000 chars per item, 20,000 chars per read, 20 search results) are gone: the constants and their validation were removed, and the tools now forward any valid JSON-object argument plus the calling turn's truncation policy to the backend, which enforces whatever limits it enforces. Treat the bound as unknown and unannounced rather than substituting a guess. Notes are *virtual* paths under `<agent_name>/notes`, not filesystem paths: reads and writes are strongly consistent, each file is capped at 1,000,000 UTF-8 bytes, and they survive context-window transitions within a rollout, which is what makes them the durable half of the pair. Both namespace descriptions instruct the model never to disclose the tools' existence, paths, storage, or contents to the user — another instruction with no gate behind it, exactly like Plan mode below. The same extension is also a *context* contributor, not only a tool source: it POSTs `alpha/notes/v2/thread_hint` carrying the calling agent's name — a subagent asks for its own hint — and any non-empty `text` it gets back becomes a `PromptSlot::ContextWindow` fragment of kind `notes.thread_hint`. It is the only producer of that slot in the whole tree, and the slot renders as the trailing line(s) of the developer-role `<context_window>` message — the one that otherwise carries the agent path and the first/previous/current context-window ids — so the hint is a developer fragment, not one of §1's user-role marked injections, and nothing in it distinguishes backend-composed text from the harness's own window bookkeeping. (The separate `token_budget.guidance_message` is *not* part of it; that renders as its own `<context_window_guidance>` fragment.) Two things are worth knowing about the 4,000-byte figure. First, it is not a client cap: `TruncationPolicy::Bytes(4_000)` is *advertised* to the backend in the `x-openai-tool-output-truncation-policy` header, and if the response still comes back over 4,000 bytes the client drops the hint entirely rather than truncating it — so a request that failed, a missing `text` field, an empty string and an overrun all produce the same thing the model sees, which is nothing. Second, only outright failure, the missing field and the overrun are recorded as `ThreadHintStatus::Failed`; an empty hint records `Succeeded`. Timing matters more than the size: the fetch happens only inside `build_initial_context_with_world_state`, which is to say whenever full context is built — the first real user turn, a new context window, and every compaction rebuild — never per turn in steady state and never per sampling step, and it is awaited inline with a 35-second backend timeout, so a hung notes backend stalls first sampling and post-compaction resume for that long with no user-visible cause. Two gates sit around this. The hint is *rendered* only when the token-budget feature is on and the turn has a resolved model context window; the contributor loop runs before that check, so a turn with no resolved window pays for the fetch and then discards the result. And with the token-budget feature on but `use_history_notes_extension` off, the same slot is filled instead by a legacy bridge that calls an MCP `notes` server's `thread_hint` tool with `wait_for_server` set — a second place a stalled backend blocks context assembly. The two paths are mutually exclusive by construction and a failed native request deliberately does not fall back to the bridge, so a `<context_window>` hint line is from exactly one of them.

Activation is not purely local, and two startup paths can set `use_history_notes_extension` with no config saying so. `apply_experimental_context` sets it outright for a ChatGPT login on a Plus, Pro or Pro-lite plan against an OpenAI-auth Codex-backend provider with the `context_management` feature enabled and no API-key/bearer/AWS provider override — enabling the `token_budget` feature itself as part of that same guard. `apply_model_defaults` then copies the catalog's `model_messages.token_budget.use_history_notes_extension` after enabling `token_budget` — but only when nothing has already spoken (no `features.token_budget` table, and no already-resolved `config.token_budget`, which the experimental path has just written if it fired) and only when managed requirements have not pinned the feature back off. Both run at thread startup, in that order, and the two activation flags stay fixed for the thread runtime even if the selected model changes later. Only the prompt halves of the budget — reminder threshold and template, guidance message, auto-compact fallback prompt and buffer — are re-resolved per turn from the active model, and only when nothing local sets them: any locally configured prompt key makes `has_explicit_settings` true and freezes all of them for the thread. A model whose defaults fail validation is logged and ignored wholesale rather than partially applied.

### Plugins as a tool and hook source

A plugin manifest is not just a marketplace listing — it can declare both `mcp_servers` and `hooks` directly, so installing a plugin can add tool surface and hook coverage in the same step, including feeding the hook auto-trust path described in Layer 0.

- A marketplace-level allowlist can deny an installed plugin's MCP tools entirely (deny-all), independent of whether the plugin itself is otherwise trusted.
- **An Agent Plugins package gets host environment variables only through a colocated `.codex-plugin/plugin.json`.** A plugin root whose `plugin.json` carries an agent-plugins.org `$schema` loads in the Agent Plugins format, and that format's `mcp.json` is closed: a stdio server declares `command`, `args`, `env` and `cwd` under `deny_unknown_fields` and has no `env_vars` field at all, while its `env` values expand only `${PLUGIN_ROOT}` and `${PLUGIN_DATA}`. So codex makes a second pass. Once the Agent Plugins servers are loaded it parses `.codex-plugin/plugin.json` — not the root manifest path, so it is read as a *legacy* manifest — and takes the MCP servers that manifest declares, either inline under its own `mcpServers` or from the file it names, defaulting to `<plugin root>/.mcp.json` when it names none. Those are merged by name and only `env_vars` is taken from a matched pair: an overlay name the Agent Plugins map does not already declare is dropped, and a pair is skipped unless both sides are stdio, so a command, its arguments and an HTTP URL are never replaced. Of the overlay's `env_vars` entries, ones marked `source: "remote"` are discarded and the rest appended. The merge also *removes* one thing: an `env` entry on the Agent Plugins server whose value is exactly `${NAME}` is dropped when both its key and the name it references match a surviving overlay variable (case-insensitively on Windows, exactly elsewhere). That removal is what makes the forwarding work at all — the literal `env` map is applied *after* the `env_vars` process-environment lookup and wins, so an unstripped `${NAME}` would overwrite the forwarded value with the placeholder string. Two boundaries: the gate is the manifest format alone, with no local-versus-remote install condition; and because the overlay's MCP files load as legacy config, the regular-file and inside-the-plugin-root checks that harden an Agent Plugins `mcp.json` are not applied to them.
- **That same file also feeds the resolved manifest's `apps`, `hooks` and `interface` — but the first two are dead on arrival.** When an Agent Plugins root manifest carries no `com.openai` extension object, `.codex-plugin/plugin.json` supplies the `apps` and `hooks` paths and replaces the `interface` block; a root `com.openai` object displaces the file for that purpose entirely. The `interface` override does reach the marketplace listing, but the `apps` and `hooks` paths never reach the runtime: every load path gates both on `PluginManifestFormat::Legacy`, so an Agent Plugins package contributes no hooks and no apps whatever those paths say. The `env_vars` overlay above is the only thing this file changes about how the plugin actually runs.
- **An attached environment is a second, independent MCP authority.** The catalog is built with per-environment authority: a pending or failed attachment resolves to `Unavailable` and contributes no environment-owned servers at all, a selection with no matching environment falls back to `SelectedPluginsOnly`, and a `Restricted` attachment disables config, compatibility and extension servers whose name and config do not match the environment's MCP policy — and denies plugin MCP registrations outright when that policy's server map is empty. This gate and the marketplace allowlist are separate: a server can pass one and be dropped by the other. The same environment is also a *source*, not only a gate: for each selected remote environment codex reads that executor's own `mcp_servers` config over the exec-server protocol and binds eligible HTTP servers into the thread, so a session can carry MCP servers that appear in no local configuration. Discovery is best effort — a failure is logged and the environment skipped — and stdio servers, servers whose HTTP headers come from host environment variables or a header helper, and every server in a Guardian-reviewer session are excluded outright. Permission authority is resolved *per server*, not once per thread. When the MCP runtime is published each enabled server is assigned exactly one profile, in this precedence: the host-owned `codex_apps` server takes the thread's own effective profile; otherwise a server whose config names an attached environment takes that environment's profile with its workspace roots materialized; otherwise a server on the local environment or a selected-plugin server falls back to the thread's profile; a non-local, non-selected-plugin server naming an environment that is not attached gets no entry at all. The order matters — an attached environment outranks the local/selected-plugin fallback, not the other way round. Only the profile is per server; the approval policy stays runtime-wide. A prepared call and an elicitation authority carry the profile resolved at publication rather than looking one up later, so a settings change cannot widen a call already in flight — but that immutability is scoped to a published runtime and a prepared call, not to the session: publication reruns the resolution and a call refreshes a dirty runtime before preparing, so the *next* call does see the new profile. Under `never`, two servers in the same turn can therefore land on opposite sides of the approval gate — one auto-approves, the other returns `requires approval` — because each is judged by its owner environment's profile rather than the primary one. A server that resolves to no profile is dropped harder than it looks: no prepared call is built for its tools and they never enter the model-visible list either, which is a defensive floor beneath the `Unavailable` catalog authority above rather than a case you will normally reach. Threadless work is a deliberate exception in the narrowing direction: standalone resource reads, the server-status snapshot, connector discovery and the app-server installed-apps listing rebuild the config with the default profile — restricted managed filesystem, restricted network — for every server, so a thread running with a Disabled or Full Access profile does not lend that authority to discovery.
- **Which curated plugin marketplace exists follows auth mode.** Under codex-backend auth the remote marketplace is targeted and the remote global catalog is active; otherwise codex falls back to the locally synced curated repo, so the same `plugin search` returns different results per login. Without codex-backend auth a plugin's declared `apps` are cleared outright, while its plain `mcp_servers` entries survive — the shadowing pass that would have removed same-named `mcp_servers` is skipped along with the apps. Managed requirements are a second input to the same question, and they can remove the curated marketplace outright. `[marketplaces] restrict_to_allowed_sources` — absent unless a requirements layer sets it — turns every marketplace source into an allowlist check, and the bundled curated source `https://github.com/openai/plugins.git` is validated against that allowlist exactly like a third-party one. Because that check passes no ref, an allowlist entry that pins a `ref` for the curated URL never admits it; a bare entry naming the same `https://` URL, or a matching host pattern, does. When it does not match, three things follow: the local curated repo sync never starts, so an existing curated checkout stops updating and a Codex home that never synced one does not get the marketplace at all — that sync path already runs only when the remote catalog is inactive, so a missing sync alone is not evidence of policy; the curated marketplace fails `validate_install`, which both filters it out of the marketplace listing and rejects an install out of it as an invalid-marketplace-file error carrying `is not allowed by requirements from`; and the policy-filtered plugin config drops every `[plugins]` entry under the two curated names `openai-curated` and `openai-api-curated`, so per-plugin config already written silently stops applying instead of erroring. That last filter carries a catch-all worth reading on its own: while restriction is on it also drops every `[plugins]` key whose marketplace is neither present in `[marketplaces]` nor one of those two curated names, again silently. `openai-bundled` is a different name that the curated branch never gates, and where it is configured it is genuinely exempt: a `[marketplaces]` entry pointing at its own managed root under `.tmp/bundled-marketplaces/` is admitted on the name-to-path match alone, without the allowlist being consulted — while that name pointing anywhere else is refused by the reserved-name rule, and a different name pointing at that root is refused on the name mismatch, neither of which consults the allowlist either. A bundled marketplace that is not configured at all leaves its `[plugins]` keys to the catch-all like anything else. The allowlist also fails closed on its own defects: a single unparseable `allowed_sources` entry makes every source validation return that compile error, curated included.
- **The Apps surface is default-on and gated only by auth.** `TurnContext::apps_enabled()` is `apps_enabled_for_auth(uses_codex_backend) && orchestrator_mcp_enabled`; `Feature::Apps` is Stable/default-on and `orchestrator.mcp.enabled` defaults to true, so auth mode is the whole story — ChatGPT-family auth gets the app tools, the `available_connectors` list and the apps-instructions fragment; an API key or Bedrock gets none of them. The hosted `codex_apps` server is contributed to every session whose `apps` feature is on, and turning `apps` off emits an explicit `Remove` for that server name rather than merely not adding it — but its *tools* still reach the model only through `apps_enabled()`, so on an API key the server is contributed and its tools are absent anyway. A `$mention`ed plugin still gets its raw MCP inventory loaded for that turn even when app tools are otherwise hidden.
- **Every `codex_apps` tool is policy-evaluated twice** — once when the menu is built, again at call time, where a disabled tool returns the literal `MCP tool call blocked by app configuration` to the model. The annotation defaults are the sharp edge: `destructive_hint` and `open_world_hint` each default to `true`, so an app tool carrying no MCP annotations is treated as both destructive and open-world and vanishes under either `apps.default.destructive_enabled = false` or `open_world_enabled = false`. A missing app tool is more often this than a broken server. Managed requirements can force an app off and force a per-tool approval mode, and the managed value beats local config.
- **Apps approval settings have a per-connected-account layer.** `apps.<app_id>.links.<link_id>` deserializes to `AppLinkConfig`, which carries exactly two keys — `approvals_reviewer` and `default_tools_approval_mode` — under `deny_unknown_fields`. An account can therefore change who reviews and whether a tool prompts, but not whether anything is enabled: `enabled`, `destructive_enabled`, `open_world_enabled` and `default_tools_enabled` stay app-level or global. Approval mode resolves managed requirement → per-tool `approval_mode` → link default → app default → `apps.default` (only when a `connector_id` was resolved) → `Auto`. Reviewer resolves managed `auto_review.required_on_models` → link → app → `apps.default`, and the reviewer that chain produces is used only if the managed `approvals_reviewer` requirement permits that value; otherwise the thread default stands. Which account is in play comes from the tool's own metadata `link_id` unless its `codex_apps` metadata sets `requires_explicit_link_id: true`, in which case the value must arrive as a non-blank string `link_id` argument on the call — a missing, blank or non-string one fails with `This app tool requires a non-empty string link_id argument` before the app-enabled check, before any approval and before the server is contacted, so it is an earlier gate than `MCP tool call blocked by app configuration`. Native approval elicitations carry the resolved `link_id` alongside `link_is_implicit`, true when the ID starts with the reserved `implicit_link::` prefix, letting an approval UI distinguish a default implicit account from an explicitly chosen one. All of this is `codex_apps`-only; a custom `mcp_servers` entry never resolves a link.
- **MCP tool availability.** An MCP server's tools can be present in one sampling step and absent from the next. Optional servers get at most a shared startup grace — `mcp_optional_startup_grace_ms`, default 1000 ms — and are then omitted from the captured catalog with only a trace log, though their startup keeps running in its own task and they list normally in a later capture once it finishes. That grace is spent once per server rather than re-granted per capture, so a server that burned it during the first capture gets effectively no wait in later ones; only a *dormant* server gets a fresh window. Setting the knob to `0` removes the shared grace instead of shortening it: an optional server with no cached tools is then awaited to its own `startup_timeout_sec` (30 s when unset), which is longer, not shorter — while a server that already has a cached catalog short-circuits ahead of either path. A live config refresh carries a new grace value into the session, and the per-server cache re-keys its stored deadline whenever that value changes. The only servers forced through startup are ones marked required in config unless they are dormant with a cached catalog, names on the turn's `required_servers` list, the Codex Apps server when it has no cached tools, and a selected-plugin server *only* when its plugin ID is in the turn's `required_plugins` set — populated by an explicit plugin mention (a structured `plugin://` mention or its `@` plaintext link) and not collected at all in a Guardian-reviewer or internal-Guardian session. An unmentioned selected-plugin server is an ordinary optional server. A server with a cached catalog is published before it is up, with each tool's `read_only_hint` cleared as unreliable — so a tool can sit in your menu and still fail with `is not available to the model`, and a cached tool loses the annotation that would otherwise have skipped its approval prompt. A server that finishes starting can still contribute nothing: `tools/list` enumeration is bounded by that server's startup timeout (30 s when unset), 100 pages, a 64 KiB pagination cursor, no repeated cursor, and 2,048 tools (8,192 for Codex Apps), and every one of those aborts the whole listing rather than truncating it.
- **An MCP connection is keyed by an explicit identity, and authentication is part of it.** `has_same_connection_config` compares exactly these fields of `McpServerConnectionIdentity`: the server's configured `auth` (`oauth` or `chatgpt`), transport, `environment_id`, host plugin root, resolved environment, local-stdio fallback cwd, referenced environment variables, runtime auth and its token, the Codex Apps cache identity, the client's elicitation capability and MCP extensions, the agent-plugin flag, and — only for the narrow stored-OAuth shape — the credential store/keyring pair and the effective `McpOAuthRefreshMode`. `reusable_client` returns `None` on any difference, so changing `mcp_servers.<name>.auth`, or flipping the under-development `mcp_oauth_refresh_coordination` feature (default off gives `Legacy`, on gives `Coordinated`), starts the server again instead of reusing the live client. The refresh mode enters identity only when the server actually resolves to stored OAuth credentials — no runtime auth provider, not a `chatgpt`-auth server on a non-local environment, a `streamable_http` transport, no `bearer_token_env_var`, and no `Authorization` supplied through `http_headers` or a resolvable `env_http_headers` entry — so it is always absent for a stdio server, and toggling that feature never disturbs one. Tool policy and presentation metadata are deliberately excluded, as the struct's own comment says: `metadata`, `tool_filter` and `tool_timeout` live on the published `McpServerView` and change without reconnecting. The identity also carries two fields that comparison skips — the stored OAuth credential snapshot and its contention flag — which `reusable_client` weighs on its own afterwards. Two further reuse conditions sit outside identity in the other direction: `startup_timeout` is a startup-only budget checked only for a connection that has not finished starting, so changing it never replaces a ready one, while a changed `catalog_item_limit` does drop reuse.
- **Hosted ChatGPT auth is refused outright for a non-local MCP server that brings no `Authorization` header of its own.** `make_rmcp_client` rejects before opening any transport when the server's `auth` is `chatgpt`, its `environment_id` is not the default `local`, and `has_explicit_http_authorization` is false: ``executor-owned MCP server `<server>` cannot use hosted ChatGPT authentication; configure executor-owned credentials instead``. That predicate is stricter than the test the identity path runs for the same question — it demands a `streamable_http` transport carrying a non-empty, control-character-free `Authorization` entry in the inline `http_headers` map, and returns false outright if `bearer_token_env_var` is set or `env_http_headers` is non-empty for *any* header name, whereas the identity path accepts an `Authorization` resolved out of `env_http_headers`. Config parsing separately refuses `http_headers_helper` on a non-local server, so the only shape that clears the guard is a literal header value written into `config.toml`, and a stdio transport cannot clear it at all. The message is not what a client reads verbatim: the error is not flagged authentication-required, so `mcp_init_error_display` falls through to its generic branch and wraps it as ``MCP client for `<server>` failed to start: …``, which leaves as an `McpStartupUpdateEvent` carrying `McpStartupStatus::Failed` — reaching the client and never the model's context.
- **Model-catalog confirmation policies reach two servers only.** The catalog's `browser_use` and `computer_use` confirmation-policy Markdown is attached verbatim to outgoing MCP calls under an `openai/confirmation_policies` request-meta key, but only for `node_repl` and `cua_repl`, and never from a Guardian-reviewer session. The text follows the *issuing step's* model snapshot, so a call that waited on an approval carries the policies of the step that issued it rather than the current one. An eligible call with no configured policies still gets an empty object, which clears whatever defaults the runtime set at startup — omission and emptiness are different signals here. This is catalog-driven behavior of the same kind Layer 0 describes, not a local config knob.
- **MCP servers can prompt the user themselves.** A server can issue an elicitation — a server-initiated request for user input — mid tool call, and codex answers some of them without asking anyone. Under approval policy `never` every elicitation is auto-declined, but a confirm-style elicitation with an empty schema is auto-accepted *first* whenever the MCP permission prompt is already auto-approved, so an unattended run neither surfaces nor honors a server's own consent prompts. A server may also mark an elicitation `codex_strict_auto_review`, which routes it to the configured automatic reviewer and fails closed — an unavailable, malformed or disallowed review returns a decline telling the caller to get explicit user approval first. That fail-closed guarantee holds only where Guardian is actually consulted. The core reviewer's two shortcuts below are evaluated *before* its strict branch, and each returns an accept carrying the same `approvals_reviewer: auto_review` meta a real review would have set — precisely the shape the strict branch validates — so a strict-auto-review empty-schema form that hits either shortcut is accepted with no inference at all, and its response reports an automatic review that never ran.
- **Two layers answer an elicitation, in order, and three shortcuts bypass review.** The MCP router decides first: an auto-deny switch, then a flat decline of anything carrying a `tool_suggestion` approval kind, then strict-auto-review, then auto-accept of an empty-schema standard form, then full-access form surfacing, then a policy decline — and only then does it hand the request to the core reviewer. The core reviewer is not terminal: when it returns no decision the router forwards the elicitation to the client, which is how an ordinary form reaches a human at all. The core reviewer runs its own order: Full Access and user-CUA shortcut, strict-auto-review branch, policy match, Guardian routing. Full Access is a specific state, not a mood — approval policy `never` *and* a disabled permission profile on the thread and on every selected environment, so `danger-full-access` under `on-request` is not it. The three shortcuts are (1) **Full Access**, which approves any empty-schema form outright, and short-circuits a second time inside `run_guardian_review` for anything that reaches it; (2) the **user-CUA shortcut**, which auto-approves the same empty-schema shape for a `user`-reviewer session running a `js` call on a `node_repl`/`cua_repl` server under connector `node_repl` with an `mcp_tool_call` approval kind — but only when the elicitation is marked neither `codex_sensitive_action` nor `codex_requires_user_input`; and (3) **`codex_sensitive_action` itself**, which is not a review gate. It does exactly three things: it disqualifies the user-CUA shortcut, it sets `require_synchronous_review`, and that flag disables extension fast approval so an installed extension cannot satisfy the review. It does not opt the action into review, and it does not override the earlier Full Access shortcut. Read its effect per reviewer rather than as a rule: under the default `user` reviewer it never causes a Guardian review, because routing returns before Guardian is consulted, and outside the narrow user-CUA shape it changes nothing at all unless the same elicitation is *also* marked `codex_strict_auto_review` — that branch runs earlier and does not consult the session's reviewer, so the marker rides into Guardian on it and strips extension fast approval there. On the user-CUA shape it is the difference between a silent auto-approval and a form the human is asked to answer. Keep it distinct from `codex_strict_auto_review`, which is the marker that *does* opt into automatic review. One input to all of this is per server rather than per thread: the auto-accept check is made against the *calling server's own* captured permission profile, the strict-auto-review branch turns only on the approval policy and the reviewer handle, and an elicitation from a server with no resolved owner profile is declined outright, ahead of both that branch and the policy check.
- **Three form families exist, and each is accepted, surfaced and declined differently.** Standard MCP `elicitation/create` forms are the only shape ever auto-accepted, and only with an empty schema. Legacy `openai/form` requests are handled only when the client declared that extension, and are never surfaced as a full-access form. The third family, `openai/elicitation/create`, is enabled only when the client's `openai/elicitation` capability is an object carrying an object-valued `form` key — the initialize path retains only that one key of whatever the client declared. Full-access form surfacing — the path that lets a *non-empty* schema still reach a human in a session whose MCP permission prompt is already auto-approved, where policy would otherwise decline it — is armed once at thread start rather than per call: the client must have declared `openai/standard-form-input`, the thread source must be `User`, and the session must be the root agent. It also refuses any elicitation carrying `codex_approval_kind`, so a privileged approval request can never be forwarded as an ordinary form. The TUI declares none of these three extensions, so it does not receive an OpenAI form variant in practice; its routing resolves one as `Decline` if it arrives.
- Two configuration knobs shape MCP exposure directly: a server's `omit_tools_from` removes it from any of the three exposure surfaces independently (`direct`, `deferred`, `code_mode`), and `code_mode.direct_only_tool_namespaces` strips the deferred and code-mode surfaces from a whole namespace. Neither emits a model-visible notice.
- Four distinct context fragments exist purely to describe plugin state to the model — installed apps, available plugins, recommended plugins, and a general plugin-instructions fragment — none of which are named anywhere else in this document; they sit alongside the fragments enumerated in §1.
- The model has a dedicated tool to request that a plugin be installed on its behalf, rather than only being able to describe the need in text.
- Plugin script attribution — crediting which script inside a plugin performed an action — is an analytics/UI concern only. It doesn't change gating and isn't covered further here.

### Collaboration / Plan mode

Plan mode is the clearest example in this document of an instruction that reads like a wall but isn't one.

- The mode's template tells the model, in plain language, that it must not perform mutating actions. That instruction lives entirely in prompt text.
- There is no dispatch-side enforcement of it: the code paths that actually route `exec` and `apply_patch` calls to execution have no branch that checks which collaboration mode is active. Plan mode's restriction is enforced by the model choosing to comply, exactly like any other instruction in this document that isn't backed by a gate.
- Contrast this with `update_plan`, which is hard-blocked in code — a genuine gate, not a prompted convention. The gap between these two is the thing this whole section exists to teach: read every instruction and ask whether a gate backs it, because some don't.
- That gate guards a tool most sessions do not have. `update_plan` is opt-in: registration is conditional on `config.update_plan_enabled`, which is true only when `[tools.update_plan] enabled = true` is set in config. An absent table resolves false and so does an unset `enabled`, so the tool is simply missing from a stock session — and the Plan-mode rejection fires only in the sessions that opted in.
- With the tool off, codex removes its own checklist guidance from the prompts it owns, so the model is never told to use a tool that is not there. The filter drops whole `` ## `update_plan` ``, `## Plan tool` and `## Plan Mode vs update_plan tool` sections; a `## Planning` section only when its body actually carries the checklist text (`You have access to an `update_plan` tool` or `When `update_plan` is available, follow this section`), so a generic planning heading survives. It also drops a `Progress visibility:` line whose next line starts `If update_plan is available`, and `- Use the plan tool ` / `- If you create a checklist or task list,` bullets together with their indented continuation lines.
- It runs on the model instructions, on the rendered base instructions — which is the copy compaction, remote compaction and Guardian feedback read, so those inherit the stripping — on built-in collaboration-mode presets, on the multi-agent role text a subagent inherits (bundled, or catalog-supplied when a catalog provides it), and on the goal continuation template.
- The stripping is confined to codex-owned text, deliberately, and the guard differs per site. A configured multi-agent role string returns before the filter. The model instructions are filtered only when no base instructions were configured or theirs carry `Model` provenance; the rendered base instructions only when that provenance is `Model`. A custom model catalog suppresses the filter on the model-instructions, base-instructions and session-side multi-agent paths — though the spawn-side usage-hint fallbacks key on `update_plan_enabled` alone, without that catalog guard, so the two can diverge under a custom catalog. A collaboration-mode override is filtered only when it matches a built-in preset in full, never on a heading custom text might also use; when the instructions come from catalog messages instead, the filter is suppressed precisely when the catalog is a custom one. Caller-authored instructions that mention `update_plan` therefore survive into a session where the tool does not exist.
- The `<collaboration_mode>` fragment that would carry the "no mutating actions" instruction is not even sent in a default session — a plain default session gets `<permissions instructions>` but no collaboration-mode fragment at all. Plan mode's soft restriction only comes into play once collaboration mode has been explicitly turned on in the first place.
